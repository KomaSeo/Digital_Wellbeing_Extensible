# 할 일을 GTD 방식으로 정리하기: 설계안

이 문서는 할 일 플래너를 GTD 방식에 맞게 바꾸는 설계안입니다. 아직 코드는 바뀌지 않았습니다.
소유자는 "할 일을 GTD에 맞춰서 정리할 수 있도록 프로그램 변경 --> 디자인을 해오도록"이라고 요청했습니다.
소유자는 이 문서를 읽고 무엇을 만들지 정합니다(5장). 지금의 동작은 [`task_planner.md`](task_planner.md)에 있습니다.

---

## 0. 이 문서에서 쓰는 말

| 말 | 뜻 |
|---|---|
| **GTD** | 데이비드 앨런(David Allen)이 책 "Getting Things Done"에서 설명한 일 정리 방법입니다. 머릿속의 일을 모두 믿을 수 있는 목록으로 옮기고, 목록을 정기적으로 살펴서, 그때그때 할 일을 고르는 방법입니다. |
| **항목** | 사용자가 목록에 적는 것 하나입니다. 지금의 할 일(`TodoItem`) 하나가 항목 하나입니다. |
| **목록 종류** | 이 설계안이 항목마다 새로 붙이는 값입니다. 항목이 수집함, 다음 행동, 기다리는 일, 언젠가 중 어디에 있는지를 나타냅니다(3.1절). |
| **AI의 목록** | AI에게 질문할 때 함께 보내는 남은 할 일의 목록입니다. 코드의 `todos_text`가 할 일 하나를 한 줄로 만듭니다. 이 목록은 조건을 보여 주고 메모는 보여 주지 않습니다. |
| **심사** | 엄격 모드에서 AI가 할 일 변경을 생활 규칙에 비추어 승인하거나 거절하는 것입니다(`PROPOSAL_PROMPT`). |
| **가짜 할 일** | 사용자가 적지 않았는데 agent가 AI의 목록에 넣는 할 일입니다. 지금은 "Improve: …"(`polish:`)만 있습니다. |
| **토큰** | Claude가 글을 세는 단위입니다. AI 비용은 보내고 받은 토큰의 수로 정해집니다. |

## 1. GTD를 짧게 설명합니다

### 1.1 다섯 단계

| 단계 | 사람이 하는 일 |
|---|---|
| **수집**(capture) | 떠오른 일을 판단하지 않고 곧바로 한곳(수집함)에 적습니다. 머리가 일을 기억하지 않아도 되게 하는 것이 목적입니다. |
| **명료화**(clarify) | 수집함의 항목을 하나씩 꺼내 "행동이 필요한가?"를 묻습니다. 필요 없으면 버리거나 언젠가 목록에 둡니다. 필요하면 "눈에 보이는 바로 다음 행동"을 정합니다. 2분 안에 끝나는 행동은 그 자리에서 합니다(2분 규칙). |
| **정리**(organize) | 명료화한 항목을 알맞은 목록에 넣습니다: 다음 행동, 프로젝트, 기다리는 일, 언젠가, 달력. |
| **검토**(reflect) | 목록을 정기적으로 살핍니다. 가장 중요한 것은 일주일에 한 번 하는 **주간 검토**입니다. 수집함을 비우고, 프로젝트마다 다음 행동이 있는지 보고, 기다리는 일과 언젠가 목록을 훑습니다. |
| **실행**(engage) | 지금 할 행동을 고릅니다. GTD는 상황(어디에 있고 무엇이 있는가), 남은 시간, 기운, 중요도의 순서로 고르라고 합니다. |

### 1.2 목록

| 목록 | 뜻 |
|---|---|
| **수집함**(inbox) | 아직 명료화하지 않은 항목이 모이는 곳입니다. 수집함의 항목은 아직 할 일로 받아들인 것이 아닙니다. |
| **다음 행동**(next actions) | 지금 바로 할 수 있는, 구체적인 몸의 행동입니다. 예: "논문"이 아니라 "논문 3장 개요를 다섯 줄로 쓰기". |
| **프로젝트**(projects) | 행동이 두 개 이상 필요한, 원하는 결과입니다. 예: "졸업논문 제출". GTD는 진행 중인 프로젝트마다 다음 행동이 적어도 하나 있어야 한다고 합니다. |
| **기다리는 일**(waiting for) | 다른 사람에게 맡겼거나 다른 사람의 답을 기다리는 일입니다. 누구를 언제부터 기다리는지 적어 두고, 때가 되면 확인합니다. |
| **언젠가/아마도**(someday/maybe) | 지금은 하지 않기로 했지만 나중에 할지도 모르는 일입니다. 주간 검토 때만 훑습니다. |
| **달력**(calendar) | 정해진 날이나 시각에만 할 수 있는 일입니다. GTD는 달력에 "그날 꼭 해야 하는 것"만 적으라고 합니다. |
| **상황**(contexts) | 행동에 필요한 장소나 도구입니다. 예: "@집", "@컴퓨터", "@전화". 사람은 지금 상황에 맞는 행동만 봅니다. |

### 1.3 이 앱과 GTD의 가장 큰 차이

GTD에서는 사람이 실행 단계에서 스스로 행동을 고릅니다. 이 앱에서는 AI가 고르고, 사용자는 고르지 않습니다. 사용자가 고르면 게을러지기 때문입니다([`task_planner.md`](task_planner.md) 4.3절).
이 설계안은 이 차이를 그대로 둡니다. 사용자는 GTD의 수집, 명료화, 정리, 검토를 하고, 실행 단계의 "고르기"는 AI가 합니다. 그래서 사용자가 목록을 잘 정리할수록 AI가 더 나은 일을 고르고, AI의 목록도 짧아집니다.

## 2. 지금의 앱과 GTD

| GTD | 지금 있는 것 | 빠진 것 |
|---|---|---|
| 수집함 | 없습니다. 할 일 탭, AI 비서 탭, Claude Desktop에서 추가한 항목은 곧바로 할 일 목록에 들어가고, 엄격 모드에서는 추가마다 심사(AI 호출 한 번)를 거칩니다. | AI를 부르지 않는 빠른 수집. 일하는 도중에 떠오른 일을 적을 곳. |
| 명료화 | 일부 있습니다. 추가 심사가 막연한 할 일을 거절하고, 빈 칸(메모의 "무엇을 하면 끝인가", 조건, 예상 시간)을 채웁니다. | "행동이 필요한가?", "다음 행동은 무엇인가?"를 묻는 단계. |
| 다음 행동 | 할 일 목록 전체가 다음 행동처럼 쓰입니다. | 다음 행동과 다른 종류의 항목을 나누는 표시. |
| 프로젝트 | 없습니다. 할 일 하나 안의 "메모와 단계"는 한 번의 할당 안에서 하는 단계입니다. | 여러 할 일을 묶는 프로젝트, 프로젝트마다 다음 행동이 있는지의 확인. |
| 기다리는 일 | 일부 있습니다. 변경 요청 심사는 "막혔다(답을 기다림)"를 승인하고, 후속 할 일을 "Not before 날짜" 조건으로 만들 수 있습니다(`list_changes`). | 누구를 기다리는지, 언제 확인할지 적는 곳. 기다리는 동안 AI가 고르지 않게 하는 표시. |
| 언젠가/아마도 | 없습니다. 사용자는 그런 일을 목록에 넣지 않거나, 넣으면 AI가 고를 수 있고 AI의 목록이 길어집니다. | AI가 고르지 않고 AI에게 보내지도 않는 목록. |
| 달력 | 약속(시각이 정해진 일), 마감, 조건의 날짜("12월 1일 이후")가 있습니다. 반복하는 약속은 따로 만드는 중입니다. | 없음. 이 설계안은 달력을 바꾸지 않습니다. |
| 상황 | 조건("집에서만", "컴퓨터 필요")과 일하기 탭의 "지금 상황" 칸이 있습니다. AI가 둘을 맞춰 봅니다. | 없음. 조건이 이미 상황의 역할을 합니다. |
| 반복하는 일 | 반복하는 할 일(`repeat`)이 있습니다. | 없음. |
| 주간 검토 | 통계 탭의 "앞으로 7일 계획"이 시간이 얼마나 필요한지 보여 줍니다. | 목록을 훑고 고치는 정기적인 검토. |
| 실행 | AI가 마감, 중요도, 조건, 지금 상황, 다음 약속까지의 시간을 보고 고릅니다. GTD의 네 기준과 거의 같습니다. | 없음. |

정리하면, 이 앱에는 실행과 달력과 상황이 이미 있고, **수집함, 기다리는 일, 언젠가, 프로젝트, 주간 검토**가 빠져 있습니다.

## 3. 제안하는 설계

이 장은 4장의 안 B(추천안)를 설명합니다. 안 A와 안 C는 이 설계에서 무엇을 빼거나 더하는지로 4장에서 설명합니다.

### 3.1 데이터

항목(`TodoItem`)에 칸을 더하고, `planner.json`에 프로젝트 목록을 더합니다.

```rust
pub enum TodoList { Inbox, Next, Waiting, Someday }   // 없으면 Next

pub struct TodoItem {
    // 지금의 칸(id, title, notes, constraints, deadline, priority, estimate_minutes, repeat …)
    pub list: TodoList,                  // 목록 종류
    pub project_id: Option<String>,      // 속한 프로젝트
    pub waiting_for: String,             // 기다리는 일: 누구(무엇)를 기다리는가
    pub follow_up: Option<NaiveDate>,    // 기다리는 일: 이 날이 되면 다시 확인한다
    pub list_since: Option<DateTime<Utc>>, // 지금의 목록 종류가 된 때(수집함이 오래됐는지, 오래 기다렸는지)
}

pub struct Project {
    pub id: String,                      // "j" + 밀리초
    pub title: String,                   // 원하는 결과. 예: "졸업논문 제출"
    pub notes: String,
    pub deadline: Option<NaiveDate>,
    pub state: ProjectState,             // Active, Someday, Finished
}
// PlannerConfig에 projects: Vec<Project>, PlannerState에 last_weekly_review를 더합니다.
```

- 모든 새 칸에는 기본값이 있으므로, 지금의 `planner.json`은 그대로 읽힙니다. 지금의 할 일은 모두 다음 행동이 됩니다(3.10절).
- 수집함의 항목에는 제목만 있어도 됩니다. 마감, 중요도, 조건은 명료화할 때 채웁니다.

### 3.2 수집: AI를 부르지 않는 빠른 입력

- 일하기 탭 맨 위에 한 줄 칸 **"떠오른 일 적기"**를 둡니다. 사용자가 적고 Enter를 누르면 그 항목이 수집함에 들어갑니다. 지금 할 일의 화면은 바뀌지 않습니다. Focus 앱이 화면을 덮는 동안(할 일을 기다리는 잠금, 일시 정지, 보고 기다리기)에도 이 칸은 쓸 수 있습니다.
- 할 일 탭, AI 비서 탭, Claude Desktop에도 "수집함에 넣기"를 둡니다.
- **수집은 엄격 모드에서도 심사하지 않습니다.** 심사가 있는 이유는 할 일이 앱을 여는 길이 되기 때문입니다. 수집함의 항목은 AI가 고르지 않으므로 앱을 열 수 없습니다. 그래서 수집은 AI 비용이 들지 않습니다.
- 수집함은 100개까지, 제목은 120글자까지 받습니다. 이 수는 AI가 정한 값이며 바꿀 수 있습니다.

### 3.3 명료화: 수집함 정리

수집함을 정리할 시간도 AI가 정합니다.
- 수집함이 비어 있지 않으면, agent는 AI의 목록에 가짜 할 일 한 줄을 넣습니다. 예: `[inbox:] 수집함 정리 | 7 items, oldest 3 days | estimate 15 min`. 이 줄은 "Improve: …"처럼 질문의 바뀌는 부분에 들어가므로 프롬프트 캐시를 깨지 않습니다. 수집함 항목의 제목은 AI에게 보내지 않습니다.
- 할 일 고르기 지시문(`PICK_PROMPT`)에 "수집함이 쌓이거나 오래되면, 일의 사이에 짧게 수집함 정리를 배정하라"를 더합니다.
- 수집함 정리가 지금 할 일이면, 일하기 탭은 수집함 항목을 하나씩 보여 주고 다음을 묻습니다.

| 사용자의 답 | 결과 |
|---|---|
| 행동이 필요 없다 | **버리기** 또는 **언젠가로**. 심사하지 않습니다. |
| 다른 사람을 기다린다 | 누구를 기다리는지와 확인할 날을 적어 **기다리는 일로**. |
| 내가 한다 | 다음 행동의 제목(동사로 끝나는 구체적인 행동), 프로젝트(고르거나 새로 만들기), 그 밖의 빈 칸을 적어 **다음 행동으로**. |

- 다음 행동과 기다리는 일로 보낸 항목은 지금의 추가 심사를 받습니다. 그래서 AI가 빈 칸(메모, 조건, 마감, 중요도, 예상 시간)을 지금처럼 채웁니다.
- **여러 항목을 한 번에 심사합니다.** 사용자는 수집함 정리의 끝에 **정리한 것 보내기**를 누르고, agent는 다음 행동과 기다리는 일로 보낼 항목을 질문 하나에 모아 AI에게 보냅니다. 지금은 추가마다 남은 할 일 목록 전체를 따로 보내므로, 다섯 항목을 한 번에 보내면 목록을 네 번 덜 보냅니다.
- 수집함 정리의 "끝냈다"는 수집함이 비었으면 심사하지 않고 바로 기록합니다. 프로그램이 직접 확인할 수 있기 때문입니다.

### 3.4 정리: 할 일 탭

할 일 탭의 맨 위에 목록 종류를 고르는 단추 줄을 둡니다: **다음 행동**, **프로젝트**, **기다리는 일**, **언젠가**, **수집함**. 각 단추에는 항목 수가 붙습니다.
- **다음 행동**은 지금의 할 일 목록과 같습니다. 줄마다 프로젝트 이름이 작게 붙습니다.
- **프로젝트**는 프로젝트마다 원하는 결과, 마감, 남은 다음 행동의 수를 보여 줍니다. 다음 행동이 없는 진행 중 프로젝트에는 빨간 "다음 행동 없음"이 붙습니다.
- **기다리는 일**은 누구를 기다리는지, 기다린 날 수, 확인할 날을 보여 줍니다.
- 항목을 펼치면 지금의 **고치기**, **지우기** 옆에 **옮기기**(목록 종류 바꾸기)가 있습니다. 옮기기가 심사를 받는지는 3.9절의 표를 따릅니다.
- 약속은 지금처럼 목록 아래에 있습니다.

### 3.5 실행: AI가 고르는 것

| 목록 종류 | AI의 목록에 들어가는가 | AI가 고를 수 있는가 |
|---|---|---|
| 다음 행동 | 지금처럼 한 줄씩 들어갑니다. 프로젝트에 속하면 줄 끝에 `P3`처럼 프로젝트 번호가 붙습니다. | 예 |
| 수집함 | 항목은 들어가지 않고, 가짜 할 일 "수집함 정리" 한 줄만 들어갑니다. | 수집함 정리만 |
| 기다리는 일 | 들어가지 않습니다. 확인할 날이 되면 그 항목은 저절로 다음 행동으로 돌아옵니다(3.6절). | 아니요 |
| 언젠가 | 들어가지 않습니다. | 아니요 |

- 질문의 앞부분(캐시되는 부분)의 할 일 목록 앞에 진행 중 프로젝트를 한 줄씩 넣습니다. 예: `[P3] 졸업논문 제출 | due 2026-12-15`. AI는 프로젝트의 마감을 보고, 마감이 가까운 프로젝트의 다음 행동을 먼저 고를 수 있습니다.
- 언젠가 목록의 항목이 AI의 목록에서 빠지므로 질문마다 토큰이 줄어듭니다. 할 일 한 줄은 조건의 길이에 따라 약 40~60토큰입니다. 언젠가 항목이 20개이면 질문마다 약 1,000토큰이 줄어듭니다. 프로젝트 줄은 프로젝트마다 약 15토큰, 프로젝트 번호는 줄마다 약 3토큰이 늘어납니다.

### 3.6 기다리는 일

- 사용자가 다음 행동을 기다리는 일로 옮기려면 누구(무엇)를 기다리는지 적어야 합니다. 확인할 날을 비워 두면 심사의 AI가 정합니다.
- 변경 요청 심사가 "막혔다(답을 기다림)"를 승인할 때, AI는 지금처럼 "Not before" 후속 할 일을 새로 만드는 대신 그 할 일을 기다리는 일로 옮기고 확인할 날을 적습니다(`list_changes`에 "기다리는 일로 옮기기"를 더함). 그래서 같은 일이 두 줄로 남지 않습니다.
- 확인할 날이 되면, agent는 그 항목을 다음 행동으로 되돌리고 제목 앞에 "확인: "을 붙입니다. 예: "확인: 지도교수님의 3장 답장". AI는 이 항목을 짧은 확인(메일함 보기, 재촉 메시지 보내기)으로 배정합니다. 끝냈다고 보고할 때 사용자가 이유에 "답이 왔다, 다음은 …"이나 "아직 안 왔다, 금요일에 다시"를 적으면, 변경 요청 심사가 `list_changes`로 다음 행동을 만들거나 다시 기다리는 일로 옮깁니다. 새 AI 호출은 들지 않습니다.
- 기다리는 일에서 다음 행동으로 사용자가 직접 옮기는 것은 심사하지 않습니다. 일이 늘어나는 쪽이기 때문입니다.

### 3.7 프로젝트와 다음 행동

- 프로젝트를 만드는 것은 심사하지 않습니다. 프로젝트 자체는 AI가 고르지 않기 때문입니다. 프로젝트에 다음 행동을 넣는 것은 지금의 추가 심사를 받습니다.
- 한 할 일이 여러 번의 할당에 걸쳐도(예: 240분짜리 "논문 3장 초안") 그것만으로 프로젝트가 되지는 않습니다. 프로젝트는 서로 다른 행동이 두 개 이상 필요할 때 씁니다. 도움말 탭에 이 기준을 적습니다.
- 프로젝트의 마지막 다음 행동을 끝냈다고 보고할 때, 일하기 탭의 완료 보고에 **"이 프로젝트의 다음 행동"** 칸이 나옵니다. 사용자가 적으면 그 행동이 "끝냈다"의 심사 안에서 `list_changes`로 추가됩니다. 그래서 추가 심사를 따로 부르지 않습니다. 사용자가 비워 두면 그 프로젝트는 "다음 행동 없음"으로 표시되고, 주간 검토가 그것을 다룹니다.
- 결과를 이룬 프로젝트는 **프로젝트 끝내기**로 닫습니다. 남은 다음 행동이 없으면 심사하지 않습니다. 남은 다음 행동이 있으면 그 행동을 지우는 것과 같으므로 심사합니다.

### 3.8 주간 검토

- 마지막 주간 검토에서 6일이 지나면, agent는 AI의 목록에 가짜 할 일 `[review:] 주간 검토 | estimate 45 min`을 넣습니다. 언제 할지는 AI가 생활 규칙(예: "주간 검토는 일요일 저녁에 한다")에 맞춰 정합니다.
- 주간 검토가 지금 할 일이면, 할 일 탭 맨 위에 프로그램이 계산한 점검표가 나옵니다. 이 점검표에는 AI가 들지 않습니다.
  1. 수집함이 비었는가(남은 수).
  2. 진행 중 프로젝트마다 다음 행동이 있는가(없는 프로젝트의 목록).
  3. 확인할 날이 지났거나 14일 넘게 기다린 기다리는 일.
  4. 언젠가 목록 전체(사용자가 훑고, 할 것은 다음 행동으로 옮김).
  5. 앞으로 14일의 약속과 마감.
- 사용자는 점검표를 보며 평소의 옮기기와 추가를 합니다. 그 변경은 3.9절의 표대로 심사받습니다.
- 주간 검토의 "끝냈다"에는 점검표의 결과가 증거로 저절로 붙고, 지금의 "끝냈다" 심사가 판단합니다. 1번과 2번이 남아 있으면 AI는 거절할 수 있습니다.
- AI가 언젠가 목록과 프로젝트를 읽고 제안하는 검토는 안 C에 넣었습니다(4장).

### 3.9 엄격 모드: 목록 사이를 옮길 때의 심사

설정 단계(엄격 모드를 켜기 전)에서는 지금처럼 모든 변경이 심사 없이 바로 적용됩니다. 엄격 모드에서는 다음 두 원칙으로 정합니다.
- **AI가 고를 수 있게 되는 쪽**(다음 행동으로 들어가는 것)은 처음 들어가는 내용이면 심사합니다. 할 일이 앱을 여는 길이 되기 때문입니다.
- **AI의 목록에서 일을 빼는 쪽**(다음 행동을 기다리는 일, 언젠가, 지우기로 보내는 것)은 심사합니다. 일을 피하는 길이 되기 때문입니다. 특히 언젠가로 옮기는 것은 지우기만큼 쉽게 일을 피하는 방법이므로, 지시문은 마감이 있거나 다른 사람이 기다리는 일을 언젠가로 옮기는 것을 거절하게 합니다.

| 옮기기 | 엄격 모드에서 | 까닭 |
|---|---|---|
| 새 항목 → 수집함 | 바로 | AI가 고르지 않습니다. |
| 수집함 → 버리기, 언젠가 | 바로 | 아직 받아들인 일이 아닙니다. 사용자는 지금도 할 일을 아예 넣지 않을 수 있으므로, 새로 피할 길이 생기지 않습니다. |
| 수집함 → 다음 행동, 기다리는 일 | 추가 심사(빈 칸 채우기 포함, 여러 개를 한 번에) | 처음 받아들이는 일입니다. |
| 언젠가 → 다음 행동 | 추가 심사 | 언젠가 항목은 심사를 받지 않았을 수 있고, 놀이를 여는 길이 될 수 있습니다. |
| 기다리는 일 → 다음 행동 | 바로 | 일이 늘어나는 쪽이고, 내용은 이미 심사받았습니다. |
| 다음 행동 → 기다리는 일, 언젠가 | 고치기 심사(이유 4글자 이상) | 일을 피하는 길이 될 수 있습니다. |
| 기다리는 일 → 언젠가, 지우기 | 고치기 심사 | 확인을 피하는 길이 될 수 있습니다. |
| 언젠가, 수집함 안에서 고치기와 지우기 | 바로 | AI가 고르지 않는 항목입니다. |
| 프로젝트를 언젠가로 | 심사 한 번(그 프로젝트의 다음 행동이 함께 옮겨짐) | 여러 일을 한꺼번에 빼는 길입니다. |

AI가 거절한 옮기기는 지금의 할 일 변경처럼 **AI 없이 하기**(기본값: 두 시간 간격으로 세 번 확인)로 예약할 수 있습니다.
"바로" 적용되는 변경은 `machine::settings`가 방향 없음(`Neutral`)으로 바로 씁니다. 프로그램 업데이트 목록과 같은 방식입니다.

### 3.10 지금의 할 일을 옮기는 방법

- 새 버전은 `list`가 없는 할 일을 모두 다음 행동으로 읽습니다. 그래서 업데이트한 날에는 아무것도 달라지지 않습니다.
- 사용자는 할 일 탭에서 항목을 언젠가나 기다리는 일로 옮기고, 프로젝트를 만들어 묶습니다. 엄격 모드에서는 이 옮기기가 3.9절의 심사를 받습니다.
- 업데이트 뒤 한 번, 설정 단계로 돌아가지 않고도 정리할 수 있도록 **처음 정리**를 둘 수 있습니다. 이것을 둘지는 5장의 질문입니다.
- `planner.json`은 여러 PC가 동기화합니다([`sync.md`](sync.md)). 예전 버전은 `list` 칸을 모르므로 언젠가 항목도 고를 수 있습니다. 자동 업데이트가 켤 때와 하루 한 번 돌므로, 이 기간은 짧습니다.

## 5. 소유자가 정할 것

1. 세 안 가운데 어느 것을 만들까요? 안 B라면 두 번에 나누어 만들까요, 한 번에 만들까요?
2. 수집함에 넣는 것을 엄격 모드에서도 심사 없이 받을까요(3.2절)? 수집함 항목은 AI가 고르지 않으므로 이 설계안은 "예"를 제안합니다.
3. 수집함의 항목을 버리거나 언젠가로 옮기는 것을 심사 없이 받을까요(3.9절)? 아직 받아들인 일이 아니므로 이 설계안은 "예"를 제안합니다.
4. 다음 행동을 언젠가로 옮기는 것을 지우기와 같은 무게로 심사할까요, 더 엄하게(예: 마감이 있으면 언제나 거절) 할까요?
5. 수집함 정리와 주간 검토도 AI가 시간을 정하게 할까요(가짜 할 일, 3.3절과 3.8절), 아니면 사용자가 아무 때나 할 일 탭에서 하게 할까요? 사용자가 아무 때나 하게 하면 그 시간이 할당 밖의 시간이 됩니다.
6. 2분 규칙을 어떻게 할까요? GTD는 2분 안에 끝나는 행동을 명료화하는 자리에서 하라고 하지만, 이 앱에서는 수집함 정리 중에 다른 앱을 열면 창 검사가 막습니다. 이 설계안은 그런 행동을 예상 시간 5분의 다음 행동으로 넣고, AI가 짧은 일을 몰아서 배정하게 하는 방법을 제안합니다.
7. 프로젝트의 다음 행동이 여러 개일 때, AI가 아무것이나 고르게 할까요(이 설계안의 기본), 아니면 "순서대로" 표시를 두어 첫 행동만 보내게 할까요(안 C)?
8. 기다리는 일의 확인할 날이 되면 저절로 다음 행동으로 되돌릴까요(3.6절), 아니면 할 일 탭에 알림만 보여 줄까요?
9. 업데이트 뒤 지금의 할 일을 정리하는 "처음 정리"를 둘까요? 둔다면, 그때의 옮기기는 심사 없이 받을까요, AI가 제안하고 사용자가 받아들이게 할까요(AI 호출 한 번, 메모를 포함하면 입력 약 20,000토큰)?
10. 목록 종류의 화면 이름을 "수집함", "다음 행동", "기다리는 일", "언젠가", "프로젝트"로 할까요, 다른 말이 좋을까요?
