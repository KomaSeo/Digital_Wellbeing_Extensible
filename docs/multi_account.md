# 관리자 계정으로 설치하고 작업용 일반 계정에서 쓰기

이 문서는 다음 구성을 만드는 방법을 설명합니다.
- 사용자는 **일반(표준) 계정**에서 일합니다.
- 차단 프로그램은 **관리자 권한**으로 돌아갑니다. 사용자는 일반 계정에서 차단 프로그램을 끌 수 없습니다.
- 컴퓨터가 켜지면 차단 프로그램이 **자동으로** 시작합니다.
- 사용자는 모든 설정을 작업 계정에서 **Focus 앱의 설정 탭**으로 고칩니다. 사용자는 설정을 다 고친 뒤 설정을 **보호합니다**.
  설정이 보호된 뒤에도 설정 탭은 열립니다. 규칙을 더 엄격하게 만드는 변경은 바로 적용되고, 그 밖의 변경은 예약됩니다. 예약된 변경은 사용자가 이틀 간격으로 세 번 "이 업데이트가 정말 맞나요?"라는 질문에 "예"라고 답해야 적용됩니다.
  프로그램 안의 어떤 것도 보호를 끄지 못합니다(6.4절).
- 관리자 계정은 프로그램을 설치하고, 어떤 계정을 관리할지 정하고, 로그를 읽을 때만 씁니다.

**결론:** 이 구성은 가능합니다. 다만 관리자가 관리자 계정에 로그인해서 프로그램을 띄워 두고 사용자가 다른 계정에서 일하는 방식으로는
안 됩니다. 개발자는 차단 프로그램을 **Windows 서비스**로 만들었습니다.

이 문서의 순서는 다음과 같습니다. 1장은 왜 서비스가 필요한지 설명합니다. 2~3장은 무엇을 만들었고 무엇을 막는지 설명합니다.
4~6장은 설치 방법과 사용 방법을 설명합니다. 7장은 한계를 설명합니다.

> ⚠️ **주의:** 개발자는 Linux에서 Windows용 컴파일 검사만 했습니다. 개발자가 실제로 실행해 본 것은 Linux에서 agent의 로컬 API와
> 설정 다시 읽기뿐입니다. 서비스 등록, 사용자 세션 안에 프로그램 띄우기, 다른 세션의 화면 캡처는 **실제 Windows에서 아직 확인하지 않았습니다.**
> 처음 설치할 때 5장의 점검 목록을 꼭 한 번 따라 해 보세요.

## 0. 이 문서에서 쓰는 말

| 말 | 뜻 |
|---|---|
| **관리자** | Windows 관리자 계정의 비밀번호를 아는 사람입니다. 관리자는 관리자 계정으로 프로그램을 설치하고, 관리 대상 계정을 정하고, 로그를 읽습니다. 이 PC의 주인이 관리자이면서 사용자일 수도 있습니다. |
| **사용자** | 작업용 표준 계정으로 일하는 사람입니다. |
| **관리 대상 계정** | 서비스가 agent를 띄우는 Windows 계정입니다. 관리자는 설치할 때 `--manage` 옵션으로 관리 대상 계정을 정합니다(4.2절). |
| **Windows 로그인 세션** | Windows가 로그인한 계정마다 따로 만드는 작업 공간입니다. 세션마다 화면, 창, 실행 중인 프로그램이 따로 있습니다. 세션에는 번호(세션 1, 세션 2, …)가 붙습니다. |
| **데일리 웰빙(daily wellbeing)** | AI가 "지금 하는 일"을 기준으로 창을 검사하는 상태입니다. 이 앱은 하루 종일 돌고, 데일리 웰빙이 켜져 있을 때만 AI 검사가 돌아갑니다. Windows 로그인 세션과는 관계가 없습니다. 코드에서는 `session_active` 값이 이 상태를 나타냅니다. |
| **AI 검사 멈추기** | 사용자가 Focus 앱의 할 일 탭에서 변경 요청 "AI 검사 멈추기"를 보내 데일리 웰빙을 끄는 것입니다(코드의 변경 요청 `End`). AI가 그 이유를 승인해야 멈춥니다. 할 일 목록이 비어 있을 때는 agent 요청 `stop_session`도 이 일을 합니다. AI 검사를 멈춰도 항상 막을 프로그램, 항상 막을 웹사이트, 이미 걸린 차단은 그대로 적용됩니다(아래 줄들). |
| **서비스** | Windows가 부팅할 때 로그인과 상관없이 실행하는 백그라운드 프로그램입니다. 서비스는 세션 0에서 돌아갑니다. |
| **SYSTEM** | Windows에서 가장 높은 권한을 가진 내장 계정입니다. 관리자 계정보다도 권한이 높습니다. |
| **agent** | 서비스가 사용자의 Windows 로그인 세션 안에 SYSTEM 권한으로 띄우는 프로그램입니다. agent가 실제로 앱을 차단하고 AI 검사를 합니다. |
| **Focus 앱** | 사용자가 보는 작은 창입니다. 화면은 한국어입니다. 사용자는 Focus 앱으로 지금 할 일과 할 일 목록을 다루고, 변경 요청을 보내고, 설정을 고치고, 지난 기록을 봅니다. Focus 앱에는 **할 일**, **AI 비서**, **차단**, **설정**, **통계**, **도움말** 탭이 있습니다. 이 문서는 이 탭들을 할 일 탭, AI 비서 탭, 차단 탭, 설정 탭, 통계 탭, 도움말 탭이라고 부릅니다(2.1절). |
| **설정** | 블랙리스트·화이트리스트 규칙(`policy.json`), AI 집중 설정(`ai_focus.json`, API 키 포함), 할 일 플래너 설정(`planner.json`)을 합쳐서 부르는 말입니다. |
| **정규식** | 글자의 모양을 나타내는 식(정규 표현식)입니다. 예를 들어 `.*game.*\.exe`는 "game이 들어 있고 .exe로 끝나는 모든 이름"을 뜻하고, `reddit\|twitter`는 "reddit이나 twitter"를 뜻합니다. 항상 막을 프로그램과 항상 막을 웹사이트(아래 줄)는 정규식으로도 적을 수 있습니다. |
| **항상 막을 프로그램** | 설정의 블랙리스트(`policy.json`의 `blacklist`)입니다. 이 목록의 프로그램은 켜질 때마다 꺼집니다. 데일리 웰빙이 꺼져 있어도, 접근 요청이 승인되어도 꺼집니다(6.2절). |
| **항상 막을 웹사이트** | `ai_focus.json`의 `always_blocked_sites` 목록입니다. 맨 앞 브라우저 탭의 제목에 이 목록의 말이 들어 있으면, agent는 AI에게 묻지 않고 그 탭을 닫습니다. 데일리 웰빙이 꺼져 있어도 닫고, 접근 요청으로도 풀리지 않습니다([`ai_focus_rule.md`](ai_focus_rule.md) 5.12절). |
| **설정 화면 (설정 탭)** | Focus 앱의 **설정** 탭입니다. 머신 설치에서는 사용자가 이 탭에서 모든 설정을 고칩니다. 설정 탭은 설정 파일을 직접 쓰지 않고, 그 세션의 agent에게 저장을 맡깁니다(6.4절). |
| **설정 묶음** | 설정 탭이 한 번에 저장하고 적용하는 설정의 작은 단위입니다. 예: API 키, 모델, 생활 규칙, 지시문 하나, 항상 막을 프로그램, 검사 간격과 판정. 설정 탭은 묶음마다 아래에 막대를 두고, 막대에는 고친 내용의 미리 보기와 버튼(**저장**, **적용**, **고친 것 버리기**, **기본값으로 되돌리기**)이 있습니다(6.4절). |
| **임시 저장** | 설정 탭이 사용자가 고친 내용(아직 적용하지 않은 내용)을 사용자 계정의 앱 데이터 폴더에 있는 `settings_drafts.json`에 저장해 두는 것입니다. 설정 탭은 고친 뒤 1초가 지나면 자동으로 임시 저장하고, Focus 앱을 다시 켜면 임시 저장한 내용을 되살립니다. 임시 저장한 내용은 아직 설정이 아닙니다. API 키는 임시 저장하지 않습니다(6.4절). |
| **적용** | 사용자가 설정 묶음 아래의 **적용**을 눌러, 그 묶음의 고친 내용을 agent에게 보내는 것입니다. agent는 받은 내용을 설정 단계인지, 보호되어 있는지에 따라 바로 쓰거나 예약합니다(6.4절). |
| **설정 단계** | 프로그램을 설치한 직후부터 사용자가 설정을 보호할 때까지의 기간입니다. 이 기간에 설정 탭에서 적용한 변경은 바로 효력이 생깁니다(6.4절). |
| **설정 보호** | 설정 단계를 끝내는 장치입니다. 사용자가 설정 탭에서 **설정 보호하기**를 누르면, agent는 `settings_protection.json` 파일을 만듭니다. 그때부터 적용한 변경 중 규칙을 더 엄격하게 만드는 변경만 바로 적용되고, 나머지는 예약된 업데이트가 됩니다. 보호는 한 방향입니다. 프로그램 안의 어떤 화면이나 요청도 보호를 끄지 못합니다. 프로그램은 관리자 계정과 표준 계정을 구별하지 않고, 설정이 보호되어 있는지만 보고 변경을 언제 적용할지 정합니다(6.4절). |
| **설정 변경 하나(편집)** | agent는 설정 탭이나 Claude Desktop이 보낸 설정 파일을 지금 적용된 파일과 비교해서, 설정 하나하나의 변경으로 나눕니다. 예: "값 하나를 바꾼다", "목록에 이름을 넣는다", "목록에서 이름을 뺀다", "할 일 하나를 넣거나 바꾸거나 뺀다"(`machine::setting_edits`의 `Edit`: `set`, `add_items`, `remove_items`, `put_list_item`). |
| **엄격한 변경과 느슨한 변경** | 규칙을 더 엄격하게 만드는 설정 변경(더 많이 막고, 덜 허용하고, 더 자주 검사하는 변경)을 **엄격한 변경**이라고 합니다. 그 밖의 변경, 그리고 어느 쪽인지 알 수 없는 변경(API 키, 모델, 생활 규칙, 지시문 등)을 **느슨한 변경**이라고 합니다. 어느 설정이 어느 쪽인지는 6.4절의 표에 있습니다. |
| **예약된 업데이트** | agent가 바로 적용하지 않고 `settings_reservations.json`에 보관해 두는 설정 변경의 묶음입니다. 지금 적용된 설정 파일은 그대로 남습니다. 설정이 보호된 뒤 적용한 느슨한 변경이 예약된 업데이트가 됩니다. AI가 승인하지 않은 할 일 변경을 사용자가 AI 없이 하기로 한 것도 예약된 업데이트가 됩니다([`task_planner.md`](task_planner.md) 4.6절). 사용자가 확인 질문(바로 아래 줄)에 세 번 연속 "예"라고 답하면, agent는 그 변경을 그때의 설정 파일에 적용합니다(6.4절). |
| **확인 질문** | Focus 앱이 예약된 업데이트마다 묻는 "<파일>의 이 업데이트가 정말 맞나요? (n/3번째 질문)"이라는 질문입니다. 설정의 예약된 업데이트는 첫 질문이 예약하고 이틀 뒤에 오고, 다음 질문은 앞 질문에 "예"라고 답하고 이틀 뒤에 옵니다. 할 일 변경의 예약된 업데이트는 같은 질문을 두 시간 간격으로 합니다. 사용자가 한 번이라도 "아니요"라고 답하면, 그 업데이트는 거절됩니다(6.4절). |

## 1. 왜 서비스가 필요한가

### 1.1 Windows는 로그인 세션마다 화면을 분리한다

한 프로그램은 자기가 속한 Windows 로그인 세션의 화면만 볼 수 있습니다. 그래서 관리자 계정의 세션에서 도는 프로그램은
사용자 계정의 세션 화면을 볼 수 없습니다.

| 차단 프로그램이 하려는 일 | 다른 세션에 대해 할 수 있는가 |
|---|---|
| 실행 중인 프로그램 목록을 보고 강제로 끄기 | ✅ 할 수 있습니다. 관리자 권한을 가진 프로그램은 모든 세션의 프로그램을 끌 수 있습니다. |
| 사용자가 지금 보는 창 알아내기 (`GetForegroundWindow`) | ❌ 할 수 없습니다. 이 함수는 호출한 프로그램이 속한 세션의 화면에서만 동작합니다. |
| 화면 캡처 | ❌ 할 수 없습니다. 프로그램은 자기 세션의 화면만 캡처할 수 있습니다. |
| 브라우저에 Ctrl+W 보내기 (`SendInput`) | ❌ 할 수 없습니다. 프로그램은 자기 세션의 화면에만 키 입력을 보낼 수 있습니다. |

그래서 관리자 계정의 세션에서 차단 프로그램을 돌리면, 차단 프로그램은 블랙리스트에 있는 프로그램은 끌 수 있습니다.
하지만 AI 검사에 필요한 창 제목, 화면 캡처, 탭 닫기는 할 수 없습니다. 게다가 다음 문제도 있습니다.
- 관리자 계정이 계속 로그인된 상태로 남아 있어야 합니다. 컴퓨터를 다시 켜면 관리자가 다시 로그인해야 합니다.
- 차단 프로그램은 관리자가 로그인해야 시작하므로, 컴퓨터를 켤 때 저절로 시작하지 않습니다.

### 1.2 개발자가 택한 구조

```
컴퓨터 부팅
 └─ [서비스] DigitalWellbeing  (세션 0, SYSTEM 권한, 자동 시작)
       │  서비스는 2초마다 로그인한 세션 목록을 확인합니다.
       │  관리 대상 계정의 세션에 agent가 없으면, 서비스가 agent를 띄웁니다.
       │
       ├─ 사용자가 작업 계정으로 로그인함 (예: 세션 2)
       │    ├─ [agent] digital-wellbeing-service.exe agent    ← SYSTEM 권한, 세션 2 안에서 실행
       │    │      · agent는 블랙리스트 규칙과 AI 규칙을 실행하고, 세션 2의 프로그램만 차단합니다.
       │    │      · agent는 세션 2의 창 제목을 읽고, 화면을 캡처하고, Ctrl+W를 보냅니다.
       │    │      · agent는 127.0.0.1:8772 포트로 Focus 앱의 요청을 받습니다. (8770 + 세션 번호)
       │    │      · agent는 Focus 앱의 요청을 받아 C:\ProgramData\DigitalWellbeing\ 안의 설정 파일을 씁니다. 설정이 보호되어 있으면, 엄격한 변경은 바로 쓰고 느슨한 변경은 확인 질문에 세 번 "예"라는 답을 받은 뒤에 씁니다.
       │    │      · 모든 agent는 설정 파일이 바뀐 것을 3초 안에 알아채고 다시 읽습니다.
       │    └─ [Focus 앱] digital-wellbeing-focus.exe          ← 사용자 권한, 로그인할 때 자동 실행
       │           · 사용자는 Focus 앱으로 할 일 목록을 다루고, AI가 정한 지금 할 일을 보고, 변경 요청을 보내고, AI 판정을 봅니다.
       │           · 사용자는 Focus 앱의 설정 탭에서 설정을 고치고, 설정을 보호하고, 확인 질문에 답합니다(6.4절).
       │           · Focus 앱은 agent와만 통신합니다.
       │
       └─ (설치할 때와 관리 대상 계정을 바꿀 때만) 관리자 계정
              · 관리자는 관리자 권한 PowerShell이나 설치 프로그램으로 `digital-wellbeing-service.exe install`을 실행합니다(4장).
```

핵심은 **서비스가 agent를 "SYSTEM 권한으로, 사용자의 세션 안에" 띄운다**는 점입니다.
- agent가 SYSTEM 권한으로 돌기 때문에, 사용자는 작업 관리자에서 agent를 끌 수 없습니다. 끄려고 하면 Windows가 "액세스가 거부되었습니다"라고 답합니다.
- agent가 사용자의 세션 안에 있기 때문에, agent는 그 세션의 화면을 보고, 캡처하고, 키 입력을 보낼 수 있습니다.

어린이 보호 프로그램이나 원격 지원 프로그램도 흔히 이 방식을 씁니다. 구현 방법은 `apps/service/src/spawn.rs`의 `spawn_in_session` 함수 주석에 있습니다.

관리자는 **설치할 때와 관리 대상 계정을 바꿀 때 말고는 관리자 계정을 쓸 필요가 없습니다.** 사용자는 모든 설정을
작업 계정에서 Focus 앱의 설정 탭으로 고칩니다. 머신 설치에는 관리자 권한으로 설정을 고치는 별도의 창이 없습니다.

## 2. 구성 요소

### 2.1 실행 파일

| 실행 방법 | 누가 실행하는가 | 하는 일 |
|---|---|---|
| `digital-wellbeing-service.exe install` | 관리자가 처음에 한 번 실행합니다. | 프로그램을 설치합니다(4장). |
| `digital-wellbeing-service.exe run` | Windows가 부팅할 때 실행합니다. | 서비스로 돌면서 agent를 띄우고, agent가 꺼지면 다시 띄웁니다. |
| `digital-wellbeing-service.exe agent` | 서비스가 SYSTEM 권한으로 실행합니다. | 사용자의 세션 안에서 프로그램을 차단하고 AI 검사를 합니다. |
| `digital-wellbeing-focus.exe` | 사용자가 로그인하면 자동으로 실행됩니다. | 사용자가 할 일을 다루고 상태를 보는 창입니다. 화면은 한국어입니다. 창에는 탭이 다섯 개 있습니다. **할 일** 탭(제목 "데일리 웰빙")은 AI가 정한 지금 할 일과 그 진행, 변경 요청, 할 일 목록과 할 일 변경을 보여 줍니다([`task_planner.md`](task_planner.md) 7.1절). **차단** 탭은 AI 검사 상태(마지막 검사 시각, 오류), 지금 걸린 차단, 접근 요청을 보여 줍니다. 사용자는 **설정** 탭에서 모든 설정을 고치고, 설정을 보호하고, 예약된 업데이트의 확인 질문에 답합니다(6.4절). **통계** 탭은 AI 사용량과 비용, 오늘의 기록, 끝낸 할 일, 요청과 AI의 답, 최근 AI 판정을 보여 줍니다([`task_planner.md`](task_planner.md) 7.3절). **도움말** 탭은 이 프로그램을 쓰는 방법을 주제마다 설명합니다. 지금은 "Claude Desktop으로 이 프로그램 쓰기" 안내가 있습니다([`claude_desktop.md`](claude_desktop.md) 2장). |
| `digital-wellbeing-mcp.exe` | 사용자가 설정하면 Claude Desktop이 실행합니다. | Claude Desktop이 할 일을 관리하게 하는 도구 모음입니다([`claude_desktop.md`](claude_desktop.md)). |

**머신 설치는 `digital-wellbeing.exe`를 설치하지 않습니다.** `digital-wellbeing.exe`는 예전 버전에서 관리자가 설정을 고치던 창입니다.
- 설치 프로그램은 이 파일을 복사하지 않고, 시작 메뉴에 "Digital Wellbeing settings (admin)" 바로 가기를 만들지 않습니다. 릴리스 zip 파일에도 이 파일이 없습니다.
- `digital-wellbeing-service.exe install`은 예전 버전이 Program Files 폴더에 남긴 `digital-wellbeing.exe`를 지웁니다. 그 파일이 실행 중이어서 지우지 못하면, 설치기는 경고만 출력하고 다음 설치 때 다시 지웁니다.
- 누군가 소스에서 빌드한 `digital-wellbeing.exe`를 이 PC에서 실행하면, 그 창은 "설정은 관리 대상 계정의 Focus 앱 설정 탭에 있다"는 안내만 보여 줍니다. 그 창은 설정을 고치지 않고, 규칙을 실행하지 않고, 로컬 API도 열지 않습니다.
  그 창은 `DigitalWellbeing` 서비스가 등록되어 있는지로 이 PC가 머신 설치인지 판단합니다. (예전에는 `machine.json` 파일이 있는지로 판단했지만, 이 파일은 제거한 뒤에도 남고 누구나 만들 수 있어서 바꿨습니다.)
- 서비스가 없는 PC에서 실행하거나 `--standalone` 옵션을 주면, `digital-wellbeing.exe`는 한 계정에서 혼자 쓰는 **단독 실행 모드**로 돕니다. 단독 실행 모드는 소스에서 빌드해서 쓰는 사람을 위한 모드입니다(4.5절, 7장 7번).

### 2.2 설치 후 파일 위치

```
C:\Program Files\DigitalWellbeing\     실행 파일 3개(digital-wellbeing-service.exe, digital-wellbeing-focus.exe, digital-wellbeing-mcp.exe)가 있습니다.
                                       일반 사용자는 이 파일을 읽고 실행할 수만 있습니다.
C:\ProgramData\DigitalWellbeing\       SYSTEM과 관리자만 이 폴더를 열 수 있습니다.
    policy.json          블랙리스트/화이트리스트 규칙
    ai_focus.json        AI 집중 설정 (API 키 포함)
    machine.json         관리 대상 계정 목록

    planner_state.json   현재 할당, 변경 요청과 할 일 변경의 기록, 메모와 단계, 들인 시간. agent가 씁니다. (할 일 플래너)

    blocks\<사용자>.json  지금 걸려 있는 차단. 그 사용자의 agent가 씁니다. 로그아웃했다가 다시 로그인해도 차단이 이어집니다.
                         차단은 시간이 지나도 풀리지 않습니다. 사용자는 설정 탭의 차단 영역(지금 걸린 차단)에서 차단을 풀 수 있습니다.
                         설정이 보호된 뒤에는 이 풀기도 예약된 업데이트가 되므로, 확인 질문에 세 번 답한 뒤에야 풀립니다.
```

설정 탭의 임시 저장 파일은 이 폴더가 아니라 사용자 계정의 앱 데이터 폴더에 있습니다. Windows에서는 `%LOCALAPPDATA%\DigitalWellbeing\DigitalWellbeing\data\settings_drafts.json`입니다.
이 파일은 그 사용자의 Focus 앱이 쓰고, 아직 적용하지 않은 고친 내용만 담습니다. API 키는 이 파일에 쓰지 않습니다(6.4절).

## 3. 사용자가 일반 계정에서 할 수 있는 것과 없는 것

| 사용자가 시도하는 것 | 결과 | 무엇이 막는가 |
|---|---|---|
| 작업 관리자에서 agent를 끈다 | ❌ Windows가 "액세스 거부"로 막습니다. | agent가 SYSTEM 권한으로 돌기 때문입니다. |
| 서비스를 멈춘다 (`sc stop`, 서비스 관리 창) | ❌ Windows가 "액세스 거부"로 막습니다. | Windows의 기본 설정에서 일반 사용자는 서비스 상태를 볼 수만 있고 멈출 수는 없습니다. |
| 설정 파일을 직접 고치거나 API 키를 직접 읽는다 | ❌ 사용자는 폴더를 열 수 없습니다. | 설치기가 `icacls` 명령으로 ProgramData 폴더를 SYSTEM과 관리자만 쓰도록 잠갔습니다. 다만 사용자는 설정 탭에서 설정을 고치고 API 키를 볼 수 있습니다(바로 아래 줄). |
| Focus 앱의 설정 탭에서 설정을 고치고 적용한다 | **설정 단계**에서는 ✅ 바로 적용됩니다. 설정이 **보호된 뒤에는** 엄격한 변경만 ✅ 바로 적용됩니다. 느슨한 변경은 예약된 업데이트가 되고, 사용자가 이틀 간격으로 세 번 "예"라고 답하기 전까지 ❌ 적용되지 않습니다(빨라도 6일 뒤). | agent가 보호 파일(`settings_protection.json`)을 확인하고, 변경마다 방향을 판단합니다. 그래서 순간적인 충동으로 차단을 풀거나 규칙을 느슨하게 바꿔도, 지금은 얻는 것이 없습니다. 사용자는 그 변경을 서로 다른 세 날에 세 번 다시 승인해야 합니다. 프로그램 안의 어떤 화면도 보호를 끄거나 질문을 앞당기지 못합니다(6.4절). |
| 할 일 탭에서 할 일 목록을 고친다(추가, 고치기, 지우기) | AI가 생활 규칙에 비추어 승인하면 ✅ 바로 적용됩니다. 설정이 보호되어 있어도 바로 적용됩니다. AI가 거절하면 ❌ 적용되지 않습니다. | 사용자는 거절된 변경을 AI 없이 하기로 할 수 있습니다. 그 변경은 예약된 업데이트가 되어, 두 시간 간격으로 세 번 "예"라는 답을 받은 뒤에 적용됩니다([`task_planner.md`](task_planner.md) 4.6절). |
| Claude Desktop에게 설정을 바꾸게 한다 | 설정 단계에서는 ❌ Claude Desktop의 도구가 거부합니다. 설정이 보호된 뒤에는 설정 탭과 같습니다. 엄격한 변경은 바로 적용되고, 느슨한 변경은 예약된 업데이트가 됩니다. | 예약된 업데이트는 설정 탭에서 적용한 것과 똑같이 확인 질문에 세 번 "예"라는 답을 받아야 적용됩니다. 확인 질문에 답하는 도구와 거절된 할 일 변경을 밀어붙이는 도구는 없으므로, 사용자만 Focus 앱에서 할 수 있습니다([`claude_desktop.md`](claude_desktop.md)). |
| 실행 파일을 다른 프로그램으로 바꿔치기한다 | ❌ 사용자는 파일을 바꿀 수 없습니다. | Program Files 폴더에는 관리자만 쓸 수 있습니다. |
| 시작 프로그램에서 끄거나 컴퓨터를 다시 켠다 | 효과가 없습니다. 차단도 풀리지 않습니다(agent가 차단을 파일에 저장해 두고 이어서 적용합니다). | 서비스는 로그인 전에 자동으로 시작하고, 사용자가 로그인할 때마다 agent를 다시 띄웁니다. |
| agent가 어떤 이유로든 꺼진다 | 서비스가 2초 안에 agent를 다시 띄웁니다. | `Supervisor`가 agent를 감시합니다. |
| 서비스가 오류로 꺼진다 | Windows가 5초 뒤에 서비스를 다시 시작합니다(최대 3번). | 설치기가 서비스 복구 설정을 넣었습니다. |
| 8765 포트의 로컬 API로 규칙을 바꾼다 | ❌ 그 API가 열려 있지 않습니다. | 8765 API는 단독 실행 모드의 `digital-wellbeing.exe`만 엽니다. 머신 설치는 이 파일을 설치하지 않고, 서비스가 등록된 PC에서 이 파일을 실행해도 안내 창만 뜹니다(2.1절). |
| agent의 API(877x 포트)로 규칙을 바꾼다 | 설정 탭과 같습니다. 설정이 **보호되어 있으면** 느슨한 변경은 예약된 업데이트가 되고, 확인 질문에 세 번 "예"라는 답을 받기 전까지 ❌ 적용되지 않습니다. | agent의 API에는 데일리 웰빙, 할 일 플래너, 접근 요청에 관한 요청(`status`, `start_session`, `stop_session`, `assign`, `stop_use`, `resume_use`, `request_change`, `request_access`, `todo_change`, `propose_todo`, `todo_change_schedule`, `task_notes_put`)과 설정에 관한 요청(`settings_get`, `settings_put`, `settings_answer`, `settings_withdraw`, `settings_protect`)이 있습니다. agent는 `settings_put`을 받을 때마다 설정이 보호되어 있는지 확인하고 변경마다 방향을 판단하며, `settings_answer`를 받으면 질문할 때가 되었는지 확인합니다(6.4절). |
| Focus 앱을 끈다 | ✅ 끌 수 있습니다. 하지만 차단에는 영향이 없습니다. | 차단은 Focus 앱이 아니라 agent가 합니다. |
| 지금 할 일을 "유튜브 보기"라고 직접 적는다 | ❌ 적을 수 없습니다. 지금 할 일을 직접 적는 칸이 없고, 남은 할 일이 있으면 agent가 `start_session`을 거부합니다. | 할 일 플래너는 언제나 켜져 있고, 지금 할 일은 언제나 AI가 할 일 목록에서 고릅니다. 사용자가 "유튜브 보기"를 할 일로 추가하려 해도, AI가 생활 규칙에 비추어 심사합니다([`task_planner.md`](task_planner.md) 4.1절, 4.6절). |
| 다음에 할 일을 직접 고른다 | ❌ 고를 수 없습니다. 사용자는 "다른 일 받기"로 이유만 적어 보내고, AI가 승인하면 AI가 다음 할 일을 고릅니다. | 사용자가 고르면 게을러지기 때문에, Focus 앱과 Claude Desktop에는 다음 할 일을 고르는 방법이 없습니다([`task_planner.md`](task_planner.md) 4.3절). |
| 차단된 앱이나 사이트를 쓰게 해 달라고 한다 | 목적을 적어 요청하면, AI가 승인할 때만 차단이 풀립니다. | 허용된 동안에도 AI가 목적대로 쓰는지 계속 확인하고, 다르게 쓰면 다시 차단합니다. 항상 막을 프로그램과 항상 막을 웹사이트는 이 방법으로 풀리지 않습니다([`access_grants.md`](access_grants.md)). |
| AI 검사를 멈춘다(변경 요청 "AI 검사 멈추기") | 남은 할 일이 있으면 이유를 적고 AI의 승인을 받아야 합니다. 할 일 목록이 비어 있을 때만 그냥 멈출 수 있습니다. | AI 검사가 멈춰 있어도, 항상 막을 프로그램, 항상 막을 웹사이트, 이미 걸린 차단은 항상 적용됩니다. |

**전제 조건: 작업 계정이 "표준 사용자"여야 합니다.** 작업 계정이 관리자 계정이면, 사용자가 위의 장치를 모두 풀 수 있습니다.
관리자는 설정 → 계정 → 가족 및 기타 사용자 → 해당 계정 → 계정 유형 변경에서 작업 계정을 **표준 사용자**로 바꾸면 됩니다.

## 4. 설치

### 4.1 준비 (관리자 계정에서 처음 한 번)

1. 관리자는 관리자 계정을 하나 만들어 둡니다. 그리고 관리자는 작업 계정을 **표준 사용자**로 바꿉니다(3장 마지막 문단).
2. 관리자는 Rust를 설치하고 이 저장소를 빌드합니다. (GitHub 릴리스의 설치 프로그램을 쓰면, 관리자는 빌드하지 않고 설치 프로그램을 실행하면 됩니다.)
   ```powershell
   cargo build --release
   ```
   빌드가 끝나면 `target\release\` 폴더에 설치에 쓰는 `digital-wellbeing-service.exe`, `digital-wellbeing-focus.exe`, `digital-wellbeing-mcp.exe`가 생깁니다.
   같은 폴더에 단독 실행 모드의 `digital-wellbeing.exe`도 생기지만, 설치기는 이 파일을 복사하지 않습니다(2.1절).

### 4.2 설치 명령

관리자는 PowerShell을 "관리자 권한으로 실행"으로 엽니다. 그리고 다음 명령을 입력합니다.

```powershell
cd <저장소 폴더>\target\release
.\digital-wellbeing-service.exe install --manage <작업 계정의 사용자 이름>
```

- `<작업 계정의 사용자 이름>`은 작업 계정의 로그인 이름입니다. 작업 계정에서 `whoami` 명령을 입력하면 `PC이름\이름`이 나옵니다. 이 중 `이름` 부분을 적습니다.
  Microsoft 계정을 쓴다면, 사용자 이름은 화면에 보이는 이름이 아니라 `C:\Users\` 아래의 폴더 이름과 같은 경우가 많습니다.
- 관리자는 `--manage`를 여러 번 써서 여러 계정을 관리 대상으로 정할 수 있습니다. 예: `install --manage work --manage admin`은 작업 계정과 관리자 계정을 모두 관리합니다.
- 관리자가 `--manage` 대신 **`--manage-all`**을 쓰면, 관리자 계정을 포함한 모든 계정이 관리 대상이 됩니다.
- 관리자가 둘 다 빼면(`install`만 실행하면), 설치기는 `machine.json`에 적힌 관리 대상 계정을 그대로 둡니다. 처음 설치할 때는 `machine.json`이 없으므로 모든 계정이 관리 대상이 됩니다.
- 설치 프로그램(Setup)과 `install.cmd`는 계정을 묻지 않고 언제나 `--manage-all`을 넘깁니다. 그래서 설치하거나 업데이트할 때마다 관리자 계정을 포함한 모든 계정이 관리 대상이 됩니다. 소유자가 관리자 계정도 언제나 관리하기로 정했기 때문입니다. 특정 계정만 관리하려면, 관리자는 위의 `--manage` 명령을 직접 실행합니다. 다만 그 뒤에 설치 프로그램으로 업데이트하면 다시 모든 계정이 관리 대상이 됩니다.
- 서비스는 몇 초마다 `machine.json`을 다시 읽습니다. 그래서 관리 대상 계정을 바꾸면, 이미 로그인해 있는 계정에도 몇 초 안에 agent가 뜹니다.

설치기는 다음 일을 순서대로 합니다. (`install.rs` 맨 위의 주석과 같습니다.)
1. 이미 설치된 서비스가 있으면, 설치기는 그 서비스를 멈춥니다.
2. 설치기는 실행 파일 3개(`digital-wellbeing-service.exe`, `digital-wellbeing-focus.exe`, `digital-wellbeing-mcp.exe`)를 `C:\Program Files\DigitalWellbeing\`에 복사합니다.
   예전 버전이 설치한 `digital-wellbeing.exe`가 그 폴더에 있으면, 설치기는 그 파일을 지웁니다.
   그다음 설치기는 이 프로그램 폴더의 권한을 직접 정합니다. 폴더의 주인을 관리자 그룹으로 바꾸고, SYSTEM과 관리자는 모든 권한을, 일반 사용자(Users)는 읽기와 실행만 갖게 합니다. 위 폴더(Program Files)에서 물려받는 권한은 끊습니다. 그래서 작업 계정은 Focus 앱을 실행할 수는 있지만, 프로그램 파일을 지우거나 바꾸거나 권한을 고치지 못합니다. Program Files는 보통 이미 이렇게 되어 있지만, 물려받는 권한에 기대지 않으려고 설치할 때마다 다시 정합니다.
3. 설치기는 `C:\ProgramData\DigitalWellbeing\` 폴더를 준비하고 잠급니다.
   - 처음 설치할 때 이 폴더가 이미 있으면, 설치기는 그 폴더의 주인과 권한을 봅니다.
     - 주인이 Administrators나 SYSTEM이고 그 밖의 누구도 폴더에 쓸 수 없으면, 그 폴더는 예전 설치가 잠가 둔 폴더입니다(프로그램을 지웠다가 다시 설치한 경우). 설치기는 그 폴더를 그대로 씁니다. 그래서 설정, API 키, 설정 보호가 그대로 남습니다.
     - 그렇지 않으면, 설치기는 그 폴더를 `DigitalWellbeing.untrusted-<시각>`으로 옮기고 새 폴더를 만듭니다. ProgramData 아래에는 일반 사용자도 폴더를 만들 수 있으므로, 미리 만들어진 폴더에는 사용자가 심어 둔 링크나 파일이 있을 수 있기 때문입니다.
   - 업데이트(서비스가 이미 설치되어 있을 때)에는 폴더를 그대로 씁니다. 그래서 설치 프로그램을 새 버전으로 실행해도 API 키를 다시 넣을 필요가 없습니다.
   - 이 폴더나 `logs` 폴더가 다른 위치를 가리키는 링크(junction)이면, 설치기는 설치를 멈춥니다.
   - 설치기는 폴더의 소유자를 관리자 그룹으로 바꾼 뒤, SYSTEM과 관리자만 이 폴더를 쓸 수 있도록 권한을 다시 씁니다. 소유자는 언제든 권한을 바꿀 수 있으므로, 소유자를 먼저 바꿔야 잠금이 유지됩니다.
   - 설치기는 이 권한을 **폴더 자체에만** 쓰고, 폴더 안의 파일과 하위 폴더는 그 권한을 물려받게 되돌립니다(`icacls <폴더>\* /reset /T`).
     rc.5까지의 설치기는 같은 권한을 폴더 안의 기존 파일에도 직접 썼습니다. 그런데 폴더용 상속 플래그가 붙은 권한은 파일에 적용되지 않아서, 업데이트할 때 이미 있던 파일(로그, 설정 파일)의 권한 목록이 비었습니다.
     권한 목록이 빈 파일은 SYSTEM도 열 수 없으므로, agent가 설정을 읽지 못하고 시작하자마자 끝났습니다(Focus 앱에는 "agent not running"이 보입니다). 지금의 설치기는 설치할 때마다 이 파일들을 고칩니다.
     예전 버전으로 이미 이 문제가 생겼다면, 관리자 PowerShell에서 `icacls C:\ProgramData\DigitalWellbeing\* /reset /T /C /Q`를 실행하고 `Restart-Service DigitalWellbeing`으로 서비스를 다시 시작하면 고쳐집니다.
4. 설치기는 관리 대상 계정을 `machine.json`에 적습니다.
5. 설치기는 `DigitalWellbeing` 서비스를 등록합니다. 이 서비스는 자동으로 시작하고, SYSTEM 권한으로 돌고, 오류로 꺼지면 다시 시작합니다.
6. 설치기는 모든 사용자가 로그인할 때 Focus 앱이 자동으로 실행되도록 등록합니다(`HKLM\...\Run` 레지스트리).
7. 설치기는 서비스를 시작합니다.

관리자가 프로그램을 업데이트하려면, 관리자는 새로 빌드한 뒤 같은 명령을 다시 실행하면 됩니다. 설치기는 기존 설정을 그대로 둡니다.
- 실행 중인 파일(예: 로그인한 사용자의 Focus 앱)은 덮어쓸 수 없으므로, 설치기는 그 파일의 이름을 `*.old`로 바꾼 뒤 새 파일을 복사합니다.
- 업데이트 도중 어떤 단계가 실패하면, 설치기는 멈춰 두었던 이전 서비스를 다시 시작합니다. 그래서 업데이트가 실패해도 컴퓨터가 차단 없이 남지 않습니다.

### 4.3 첫 설정 (작업 계정의 Focus 앱)

설치가 끝난 직후에는 설정 보호 파일이 없으므로, 설정은 **설정 단계**에 있습니다. 설정 단계에서는 적용한 변경이 바로 효력이 생깁니다. 사용자는 이때 작업 계정에서 설정을 모두 마치고 설정을 보호합니다.

1. 사용자는 작업 계정으로 로그인합니다. 로그인하면 Focus 앱이 자동으로 뜹니다.
   Focus 앱이 보이지 않으면, 사용자는 시작 메뉴의 **Digital Wellbeing Focus**를 실행하거나 알림 영역(트레이)의 Focus 아이콘을 클릭합니다.
2. 사용자는 Focus 앱의 **설정** 탭을 엽니다. Focus 앱은 agent에게서 설정을 받아 오고, 네 영역을 보여 줍니다(동작 방식은 6.4절).
   **AI 연결**(API 키, 모델, AI 하루 예산), **AI 규칙**(생활 규칙, 약속 규칙, 플래너 AI의 지시문), **차단**(항상 막을 프로그램, 항상 막을 웹사이트, 지금 걸린 차단, AI가 준 접근 허용, 접근 요청의 한도), **AI 검사**(다시 검사하기까지의 시간, 앱을 끄기까지의 판정 수, 화면 캡처, 검사하지 않을 앱 목록, 비공개 앱, 브라우저)입니다.
   설정 탭은 설정을 작은 묶음으로 나눕니다. 묶음마다 아래에 막대가 있고, 사용자는 그 막대의 **적용**을 눌러 그 묶음만 agent에게 보냅니다.
3. 사용자는 **AI 연결** 영역의 **Anthropic API 키** 칸("새 키를 붙여 넣으세요")에 Anthropic API 키를 붙여 넣고 **이 키 쓰기**를 누른 뒤, 바로 그 아래 막대의 **적용**을 누릅니다.
   - API 키는 임시 저장되지 않습니다. 그래서 사용자가 **적용**을 누르기 전에 Focus 앱을 끄면, 붙여 넣은 키는 사라집니다. 설정 탭도 "키는 자동 임시 저장에 남기지 않습니다. "이 키 쓰기" 뒤에 바로 "적용"을 누르세요."라고 안내합니다.
   - 적용하면 칸 위에 "키가 있습니다(…abcd)."처럼 키의 마지막 4글자가 보입니다. 키가 없으면 빨간 글씨로 "키가 없습니다. AI가 아무것도 판정하거나 고르지 못합니다."가 보입니다.
   - 사용자는 **키 확인**을 눌러 키가 맞는지 확인할 수 있습니다. 이 버튼은 Anthropic의 모델 목록을 조회하므로 비용이 들지 않습니다.
     "✔ 키가 동작합니다(…)"가 나오면 키가 맞습니다. "키가 받아들여지지 않았습니다: …"가 나오면 그 뒤의 오류 내용을 읽습니다. 오류 내용이 "API error 401"로 시작하면 키가 틀렸고, "API error 404"로 시작하면 설정의 모델 이름이 틀렸습니다.
   - agent는 SYSTEM 권한으로 돌기 때문에, **관리자나 사용자 계정에 설정된 `ANTHROPIC_API_KEY` 환경 변수를 읽지 못합니다.** 그래서 사용자는 환경 변수가 있더라도 이 칸에 키를 넣고 적용해야 합니다. 키가 없으면 AI 검사의 오류 줄에 "API 키가 없습니다. 설정 탭의 AI 연결에서 키를 넣고 적용하세요"가 나옵니다.
   - 프로그램은 키를 암호화하지 않고 `C:\ProgramData\DigitalWellbeing\ai_focus.json`에 저장합니다. 작업 계정은 그 폴더를 열 수 없습니다.
     하지만 agent는 설정 읽기 요청(`settings_get`)에 키를 포함한 설정을 돌려주므로, 작업 계정의 프로그램은 키를 읽을 수 있습니다. 설정 탭은 화면에 키의 마지막 4글자만 보여 줍니다.
     설정이 보호된 뒤에도 마찬가지입니다. 키를 숨겨야 한다면, 그 사람이 쓰는 계정을 관리 대상에서 빼십시오.
   - 키를 지우려면 **키 지우기**를 누르고 적용합니다. 입력한 키를 눈으로 확인하려면 **보이기**를 체크합니다.
4. 사용자는 필요하면 **차단** 영역의 **항상 막을 프로그램**에 항상 막을 프로그램(게임 등)을 넣고(블랙리스트), **항상 막을 웹사이트**에 항상 막을 웹사이트의 이름(예: `youtube`)을 넣습니다. 두 목록 모두 정규식으로도 적을 수 있습니다(6.2절).
   할 일 플래너는 언제나 켜져 있습니다. 사용자는 **할 일** 탭에서 할 일을 추가하고, **AI 규칙** 영역에서 생활 규칙을 적고 적용합니다([`task_planner.md`](task_planner.md) 8.1절). 할 일이 하나라도 있으면 AI가 지금 할 일을 고르고 AI 검사가 시작됩니다.
   플래너 AI의 지시문을 고치고 싶으면, 사용자는 같은 영역의 **AI 지시문**에서 지시문을 펼쳐 고칩니다. 설정 단계에서 적용하면 바로 효력이 생기므로, 지시문을 시험해 보기 좋은 때입니다.
5. 사용자가 고친 내용은 1초 뒤 자동으로 **임시 저장**됩니다. 임시 저장한 내용은 Focus 앱을 다시 켜도 남지만, 아직 설정이 아닙니다. 묶음 아래의 막대는 고친 내용을 하나하나 보여 주고, 각 줄 앞에 "적용하면 바로"(초록) 또는 "적용하면 예약"(노랑)을 붙입니다. 설정 단계에서는 모두 "적용하면 바로"입니다.
   사용자가 막대의 **적용**을 누르면, Focus 앱은 그 묶음의 고친 내용만 agent에게 보내고, agent가 진짜 설정 파일을 씁니다. 모든 agent는 바뀐 설정을 3초 안에 다시 읽습니다. **고친 것 버리기**를 누르면 그 묶음의 고친 내용을 버립니다.
   막대 아래에 "적용했습니다. 지금부터 효력이 있습니다."처럼 결과가 나옵니다. 설정이 보호된 뒤에 느슨한 변경을 적용하면 "예약했습니다. 첫 질문은 2026-11-03 14:05에 옵니다." 또는 "1개는 바로 적용했고, 나머지는 예약했습니다. 첫 질문은 …에 옵니다."처럼 나옵니다.
   설정 단계에서는 설정 탭 위쪽에 "설정 단계: 변경이 바로 적용되고, 이 PC를 쓰는 누구나 설정을 바꿀 수 있습니다."라는 노란 안내가 보입니다.
6. 설정을 다 고쳤으면, 사용자는 설정 탭 맨 위의 **설정 보호(잠금)** 영역에서 "프로그램 안의 어떤 것도 보호를 끄지 못한다는 것을 이해했습니다."를 체크한 뒤 **설정 보호하기**를 누릅니다. 설정 단계 동안에는 할 일 탭 맨 위에도 노란 줄과 이 영역으로 가는 링크(**설정 탭에서 보호하기**)가 나옵니다. 설정을 보호한 뒤에는 이 영역에 버튼 대신 "설정이 보호되어 있습니다. …"라는 설명만 남습니다.
   **보호는 끌 수 없습니다.** 보호한 뒤에 규칙을 느슨하게 바꾸는 설정은 빨라도 6일 뒤에 적용됩니다(이틀 간격의 확인 질문 세 개). 그래서 사용자는 보호하기 전에 설정이 원하는 대로 동작하는지 며칠 써 보며 확인하는 편이 안전합니다(6.4절).

### 4.4 우회를 막는 추가 설정 (관리자 계정에서, 권장)

이 프로그램은 Windows가 정상으로 부팅한 뒤에만 동작합니다. 그래서 사용자가 컴퓨터를 다른 방법으로 켜면 이 프로그램을 피할 수 있습니다.
이 절은 그런 길 세 가지(관리자 계정, 다른 장치로 부팅, 안전 모드)를 막는 방법을 설명합니다. 이 설정들은 이 프로그램이 하지 않고, 관리자가 직접 합니다.

**1. 관리자 계정**
- 작업은 언제나 표준 계정에서 합니다(4.1절). 관리자 계정이 있으면 서비스를 멈추거나 데이터 폴더의 파일을 지울 수 있기 때문입니다.
- 관리자 계정의 비밀번호는 길게 만들고, 사용자가 순간적인 충동으로 쉽게 꺼낼 수 없는 곳에 둡니다. 예를 들어 종이에 적어 다른 사람에게 맡기거나, 꺼내는 데 시간이 걸리는 곳에 둡니다.
- 관리자 계정은 설치, 업데이트, 관리 대상 계정 바꾸기(`install --manage`), 로그 읽기에만 씁니다.

**2. BIOS(UEFI) 비밀번호: 다른 장치로 부팅하는 길 막기**

BIOS(요즘 PC에서는 UEFI)는 Windows보다 먼저 실행되는 펌웨어 설정 화면입니다. 사용자가 USB에 담긴 다른 운영체제로 부팅하면, 이 프로그램은 실행되지 않습니다. 그래서 관리자는 BIOS에서 다음을 설정합니다.
1. PC를 켤 때 제조사가 정한 키(보통 Del, F2, F10, F12 중 하나)를 눌러 BIOS 설정 화면에 들어갑니다.
2. **관리자(Supervisor/Administrator) 비밀번호**를 설정합니다. 이 비밀번호가 있으면 비밀번호 없이 BIOS 설정을 바꿀 수 없습니다.
3. **USB·네트워크 부팅을 끄고**, 부팅 순서를 Windows가 깔린 디스크 하나만 남깁니다. 부팅 장치를 고르는 메뉴(부팅 메뉴)도 끌 수 있으면 끕니다.
4. **Secure Boot**를 켭니다.
5. 설정을 저장하고 다시 켭니다.

메뉴 이름과 위치는 제조사마다 다르므로, 제조사의 설명서를 함께 봅니다. 디스크를 다른 PC에 꽂아 읽는 것까지 막으려면 Windows의 **BitLocker**로 디스크를 암호화합니다. BitLocker 복구 키는 관리자 비밀번호처럼 사용자가 쉽게 꺼낼 수 없는 곳에 둡니다.

**3. 안전 모드로 들어가는 길 막기**

안전 모드는 Windows를 최소한의 드라이버와 서비스로만 켜는 방식입니다. 안전 모드에서는 이 프로그램의 서비스가 시작되지 않습니다.
표준 계정은 `msconfig`나 `bcdedit`로 다음 부팅을 안전 모드로 정할 수 없습니다. 그 일에는 관리자 권한이 필요하기 때문입니다.
남은 길은 로그인 화면이나 시작 메뉴에서 Shift를 누른 채 "다시 시작"을 눌러 들어가는 **고급 시작 옵션**(Windows 복구 환경, WinRE)과, 부팅에 여러 번 실패하면 자동으로 뜨는 복구 화면입니다.
관리자는 **관리자 권한 PowerShell**에서 다음 명령으로 이 길을 막습니다.

```powershell
reagentc /disable                                          # Windows 복구 환경(WinRE)을 끕니다. Shift+다시 시작으로 안전 모드에 들어갈 수 없게 됩니다.
bcdedit /set "{default}" recoveryenabled No                # 부팅에 실패해도 복구 화면으로 들어가지 않습니다.
bcdedit /set "{default}" bootstatuspolicy IgnoreAllFailures # 비정상 종료 뒤에도 복구 메뉴를 띄우지 않습니다.
bcdedit /set "{bootmgr}" displaybootmenu No                 # 부팅 관리자 메뉴를 띄우지 않습니다.
reagentc /info                                             # "Windows RE status: Disabled"가 나오면 꺼진 것입니다.
```

알아 둘 점:
- WinRE를 끄면 "이 PC 초기화", 시스템 복원, 자동 복구도 쓸 수 없습니다. Windows가 고장 나면 관리자는 Windows 설치 USB로 복구해야 합니다. 그래서 관리자는 설치 USB를 미리 만들어 두는 편이 안전합니다.
- 되돌리려면 관리자가 `reagentc /enable`과 `bcdedit /set "{default}" recoveryenabled Yes`, `bcdedit /deletevalue "{default}" bootstatuspolicy`, `bcdedit /set "{bootmgr}" displaybootmenu Yes`를 실행합니다.
- 설치 USB로 부팅하면 복구 도구를 다시 쓸 수 있습니다. 그래서 2번(BIOS 비밀번호와 USB 부팅 끄기)을 함께 해야 이 길도 막힙니다.
- 이 명령들은 사용자가 예전에 커뮤니티(Reddit)에서 찾은 방법을 개발자가 정리한 것입니다. 개발자는 이 명령들을 실제 PC에서 시험하지 않았습니다. 관리자는 실행하기 전에 중요한 파일을 백업합니다.

### 4.5 코드를 고치며 내 PC에서 빠르게 시험하기

GitHub의 릴리스를 거치면 한 번에 몇 분이 걸립니다. 코드를 고쳐 가며 시험할 때는 내 PC에서 직접 빌드하고 설치하는 편이 훨씬 빠릅니다.
첫 빌드는 몇 분 걸리지만, 그 뒤로는 바뀐 부분만 다시 컴파일하므로 수십 초면 됩니다.

준비(한 번만): 개발자는 https://rustup.rs 에서 Rust를 설치하고(기본 MSVC 선택), Visual Studio Build Tools의 "C++를 사용한 데스크톱 개발"을 설치합니다.

| 하고 싶은 것 | 명령 (저장소 폴더에서) |
|---|---|
| 자동 테스트만 돌리기 | `cargo test --workspace` |
| 서비스 없이 내 계정에서 전체 기능 써 보기 | `cargo run -p digital-wellbeing --release -- --standalone` (관리자 PowerShell) |
| 서비스까지 실제로 설치해 시험하기 | `.\scripts\dev-install.ps1 -Manage <작업 계정>` (관리자 PowerShell, 처음 한 번) |
| 고친 코드로 다시 설치하기 | `.\scripts\dev-install.ps1` |
| 다시 설치하고 agent 로그를 실시간으로 보기 | `.\scripts\dev-install.ps1 -Tail` |

`dev-install.ps1`은 릴리스 빌드를 한 뒤 `install` 명령을 실행하고, 서비스 상태와 최근 로그를 보여 줍니다. 설치기는 실행 중인 서비스를 멈추고 파일을 바꾼 뒤 다시 시작하므로, 개발자는 이 스크립트를 몇 번이고 다시 실행해도 됩니다.
PowerShell이 스크립트 실행을 막으면, 개발자는 한 번만 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`를 실행합니다.

## 5. 설치 확인 점검 목록 (처음 한 번)

사용자는 작업 계정으로 로그인한 뒤, 다음을 하나씩 확인합니다.

1. 로그인하면 **Digital Wellbeing Focus** 창이 뜨는가? 창이 뜨지 않으면, 사용자는 시작 메뉴에서 그 프로그램을 직접 실행해 봅니다.
2. Focus 창에 빨간 글씨로 "agent not running…"이 **보이지 않는가?**
3. 작업 관리자 → 세부 정보 탭에서, `digital-wellbeing-service.exe`가 **사용자 이름 SYSTEM**으로 **두 개** 있는가? 하나는 서비스이고, 하나는 agent입니다.
   사용자가 agent에서 "작업 끝내기"를 누르면, Windows가 "액세스 거부"라고 답하는가?
4. 사용자가 할 일 탭에서 **+ 할 일 추가**로 할 일을 하나 넣으면, 15초쯤 뒤 AI가 지금 할 일을 고르고 AI 검사가 시작되는가? 그리고 1분 안에 통계 탭의 "최근 AI 판정"에 판정이 나오는가?
   - 오류가 보이면(차단 탭의 "AI 검사가 실패했습니다: …"), 사용자는 오류 메시지를 읽습니다. 키가 없거나 잘못되었다면, 사용자는 4.3절 3번을 다시 합니다. 설정이 이미 보호되어 있으면, 새 키도 예약된 업데이트가 되어 확인 질문에 세 번 답한 뒤에 적용됩니다(프로그램은 키의 변경이 엄격한지 느슨한지 판단할 수 없습니다).
   - AI가 이상한 판정을 내리면, 관리자는 관리자 계정에서 `logs\agent-session<번호>.log`를 엽니다.
5. 사용자가 설정 탭의 차단 영역에서 **항상 막을 프로그램**에 `notepad.exe`를 넣고 적용한 뒤 메모장을 켜면, 1초 안에 메모장이 꺼지는가? (항상 막을 프로그램에 넣는 것은 엄격한 변경이므로, 설정이 보호되어 있어도 바로 적용됩니다.)
6. 사용자가 지금 할 일과 관계없는 사이트(예: 유튜브의 오락 영상)를 열어 두고 2분쯤 기다리면, 그 탭이 닫히는가?
7. 사용자가 **항상 막을 웹사이트**에 `youtube`를 넣고 적용한 뒤 유튜브를 열면, 몇 초 안에 그 탭이 닫히는가? 이 탭은 데일리 웰빙이 꺼져 있어도 닫혀야 합니다.

agent가 뜨지 않으면, 관리자는 관리자 계정에서 `C:\ProgramData\DigitalWellbeing\logs\service.log`를 엽니다.
이 파일의 `could not start agent for session N: …` 줄에 Windows의 오류 내용이 적혀 있습니다.

## 6. 매일 쓰는 방법

### 6.1 사용자가 하는 일

할 일 플래너는 언제나 켜져 있습니다. 사용자는 지금 할 일을 직접 적지 않고, AI가 할 일 목록에서 정해 준 할 일을 합니다.
사용자가 할 일을 끝내거나, 다른 일을 받거나, AI 검사를 멈추려면 이유를 적고 AI의 승인을 받아야 합니다. 자세한 방법은 [`task_planner.md`](task_planner.md) 8장에 있습니다.

1. 사용자가 로그인하면 Focus 창이 뜹니다. 할 일 목록에 할 일이 있으면, agent가 15초 안에 지금 할 일을 정하고 AI 검사를 시작합니다. 사용자는 할 일 탭의 **할 일 받기**를 눌러 바로 받을 수도 있습니다.
2. 할 일 목록이 비어 있으면, 할 일 탭은 "할 일 목록이 비어 있습니다. 아래의 "+ 할 일 추가"로 할 일을 넣으세요. …"라고 안내합니다. 사용자는 **+ 할 일 추가**로 할 일을 넣습니다. 쉬기와 놀기도 할 일로 넣을 수 있습니다.
3. 할 일 탭은 지금 할 일, AI가 고른 이유, 계획된 끝까지의 진행을 보여 줍니다. AI 검사는 이 할 일을 기준으로 창을 판정합니다.
4. 사용자가 할 일을 끝냈으면 **✔ 끝냈어요**를, 막혔으면 **⛔ 막혔어요**를, 쉬고 싶으면 **☕ 쉬고 싶어요**를 누르고 이유를 적어 **요청 보내기**를 누릅니다. 막혔거나 쉬고 싶을 때의 요청은 "다른 일 받기"이고, 무엇을 할지는 AI가 정합니다.
   AI 검사를 멈추고 싶으면 변경 요청 "AI 검사 멈추기"를 고르고 이유를 적습니다. 사용자가 로그아웃하거나 컴퓨터를 다시 켜도 AI 검사는 멈추지만, agent가 15초 안에 다시 할 일을 정합니다. 최근 할당이 있으면 AI를 부르지 않고 그 할 일을 이어 갑니다.
5. 일에 필요한 앱이나 사이트가 차단되면, 사용자는 Focus 창의 차단 탭에서 "접근 요청"을 누르고 목적을 적어 요청합니다. 자세한 방법은 [`access_grants.md`](access_grants.md) 10장에 있습니다.
6. 사용자가 Focus 창의 X를 누르면, 창은 닫히지 않고 **알림 영역(트레이)**으로 숨습니다. 트레이의 Focus 아이콘을 클릭하면 창이 다시 열립니다.
   아이콘을 오른쪽 클릭하면 메뉴가 나옵니다. **열기**는 창을 열고, **설정**은 창의 설정 탭을 열고, **끝내기**는 Focus 앱을 끝냅니다.
   Focus 앱을 끝내도 agent는 계속 차단합니다. 사용자가 Focus 앱을 다시 실행하면 상태가 그대로 보입니다.
   Focus 앱이 이미 트레이에서 돌고 있을 때 시작 메뉴에서 다시 실행하면, 새 창이 뜨지 않고 돌고 있던 창이 앞으로 나옵니다.
   트레이 아이콘은 `apps/focus/src/tray.rs`가 Windows API(`Shell_NotifyIconW`)로 직접 만듭니다. 아이콘은 자기 스레드에서 돌기 때문에, 창이 숨어 있어도 반응합니다. 탐색기가 다시 시작되면 아이콘도 다시 붙습니다.

### 6.2 설정을 바꿀 때

- 사용자는 작업 계정의 Focus 앱에서 설정 탭을 열고 설정을 고친 뒤 적용합니다(6.4절). 설정이 보호되어 있으면, 엄격한 변경은 바로 적용되고, 느슨한 변경은 예약된 업데이트가 되어 사용자가 확인 질문에 이틀 간격으로 세 번 "예"라고 답한 뒤에 적용됩니다.
- 확인 질문에 답할 때가 되면, Focus 앱은 창을 띄워 설정 탭을 보여 줍니다. 할 일 탭에도 "예약된 업데이트가 답을 기다립니다: 이 업데이트가 정말 맞나요?"라는 빨간 줄과 설정 탭으로 가는 링크(**설정 탭에서 답하기**)가 보입니다.
- 설정 탭은 이 앱에 필요한 설정만 네 영역으로 나눠 보여 줍니다. 각 영역의 설명 문구는 어떤 변경이 바로 적용되고 어떤 변경이 예약되는지도 알려 줍니다. 각 설정 묶음 아래에는 6.4절의 막대(**저장**, **적용**, **고친 것 버리기**, **기본값으로 되돌리기**)가 있습니다.
  - **AI 연결** (`ai_focus.json`): **Anthropic API 키**(**이 키 쓰기**, **키 지우기**, **키 확인**, **보이기**), **모델**(목록에서 고르는 메뉴. 목록은 agent가 일주일마다 Anthropic의 모델 API에서 받고, 적용할 때 agent가 그 모델이 있는지 먼저 확인합니다. [`ai_focus_rule.md`](ai_focus_rule.md) 5.15절), **AI 하루 예산**("AI 검사의 하루 예산(USD, 0 = 제한 없음)"). 지금까지 쓴 AI 사용량은 이 영역이 아니라 통계 탭에 있습니다.
  - **AI 규칙** (`planner.json`): **생활 규칙**과 플래너 AI의 지시문 네 개(**AI 지시문**: "지금 할 일과 시간 고르기", "하는 일을 바꾸는 요청 심사", "할 일 변경 심사(새 할 일의 빈 칸 채우기 포함)", "앞으로 7일 계획(날마다 일에 써야 할 시간과 여유)").
    플래너를 켜고 끄는 설정은 없습니다. 플래너는 언제나 켜져 있고, AI가 할 일 목록에서 지금 할 일을 고릅니다([`task_planner.md`](task_planner.md) 4.1절).
    지시문마다 기본 지시문의 글이 보이고, **기본 지시문을 복사해서 고치기** 버튼이 있습니다. 자기 지시문을 기본 지시문으로 되돌리려면 그 지시문 아래 막대의 **기본값으로 되돌리기**를 누르고 적용합니다([`task_planner.md`](task_planner.md) 7.2절).
  - **차단** (`policy.json`, `ai_focus.json`): **항상 막을 프로그램**(블랙리스트), **항상 막을 웹사이트**, 지금 걸린 모든 사용자의 차단(**지금 걸린 차단**)과 **차단 풀기**(예약됨)·**계속 막기** 버튼, AI가 준 접근 허용(**AI가 준 접근 허용**)과 **허용 취소**(바로 적용) 버튼, 접근 요청의 한도(**접근 요청**: "시간을 정한 허용의 최대 길이(분)", "AI가 취소할 때까지 가는 허용을 줄 수 있다").
  - **AI 검사** (`ai_focus.json`): **검사 간격과 판정**(on_task 판정을 다시 검사하기까지의 분, 0은 unsure 창만큼 자주; unsure 창을 다시 검사하기까지의 초; 앱을 끄기까지의 off_task 판정 수; 화면 캡처를 보낼지), 검사하지 않는 앱(**검사하지 않는 앱(언제나 허용)**), 화면 캡처 없이 검사하는 앱(**화면 캡처 없이 검사하는 앱(비공개 앱)**), 브라우저 목록(**브라우저(프로그램 대신 탭을 닫음)**).
- **항상 막을 프로그램은 이름이나 정규식으로 적습니다** (`crates/list_based_rule/src/lib.rs`, `crates/enforcer/src/pattern.rs`).
  - 항목에 `* + ? ( ) [ ] { } | ^ $ \` 중 하나라도 들어 있으면, 그 항목은 정규식입니다. 정규식은 대소문자를 무시하고, 프로그램 이름 **전체**와 맞아야 합니다. 예: `.*game.*\.exe`는 `mygame.exe`를 막지만 `notepad.exe`는 막지 않습니다. `(lol|valorant).*`는 `valorant-win64.exe`를 막습니다.
  - 점(`.`)만 있는 항목은 정규식이 아닙니다. 그래서 `steam.exe`는 글자 그대로의 이름이고, `steamwebhelper.exe`를 막지 않습니다.
  - 정규식이 아닌 항목은 예전처럼 프로그램 이름으로 바뀝니다(소문자로 바꾸고, 경로를 떼고, 끝에 `.exe`를 붙입니다). 정규식인 항목은 적은 그대로(소문자로만 바꿔서) 남습니다. 이름으로 바꾸면 `.exe`가 붙거나 `\`에서 잘려 정규식이 망가지기 때문입니다.
  - 정규식처럼 보이지만 정규식으로 읽을 수 없는 항목(예: `weird(`)은 글자 그대로의 이름으로 맞춰 봅니다.
  - Windows가 돌아가는 데 꼭 필요한 프로그램(explorer.exe 등)과 이 프로그램 자신의 실행 파일은 정규식에 걸려도 끄지 않습니다. 그래서 `.*`처럼 모든 이름에 맞는 정규식을 넣어도 Windows는 멈추지 않습니다.
  - 화이트리스트 모드의 목록도 같은 방법으로 맞춰 봅니다.
- **항상 막을 웹사이트는 탭 제목에 들어 있는 말이나 정규식으로 적습니다.** 대소문자는 무시합니다. 정규식이 아닌 항목은 탭 제목에 그 말이 들어 있으면 맞고, 정규식인 항목은 탭 제목의 일부와 맞으면 됩니다(예: `reddit|twitter`). 탭 제목 끝의 브라우저 이름(" - Google Chrome" 등)은 비교에서 뺍니다. 자세한 동작은 [`ai_focus_rule.md`](ai_focus_rule.md) 5.12절에 있습니다.
- 할 일 목록은 설정 탭이 아니라 할 일 탭에서 고칩니다. 할 일 변경은 AI가 심사합니다([`task_planner.md`](task_planner.md) 4.6절).
- 예전 설정 탭에 있던 화이트리스트 모드 선택, 저장한 목록 묶음(strategies), 실행 중인 프로그램 표는 없어졌습니다. 이 값들은 `policy.json`에 그대로 남아 있습니다. 기본 모드는 블랙리스트 모드입니다.
- 관리 대상 계정은 설정 탭에서 바꿀 수 없습니다. 관리 대상 계정을 바꾸려면, 관리자는 관리자 계정에서 `machine.json`의 `managed_users`를 고치거나 `install --manage …` 명령을 다시 실행합니다.

### 6.3 제거

관리자는 관리자 권한 PowerShell에서 다음 명령을 입력합니다.

```powershell
& "C:\Program Files\DigitalWellbeing\digital-wellbeing-service.exe" uninstall
```

이 명령은 서비스와 Focus 앱 자동 실행 등록을 지웁니다. 이 명령은 프로그램 폴더와 데이터 폴더를 지우지 않습니다. 관리자가 원하면 두 폴더를 직접 지웁니다.

### 6.4 설정 화면, 설정 보호, 예약된 업데이트 (작업 계정에서 설정 고치기)

머신 설치의 모든 설정은 Focus 앱의 **설정** 탭에서 고칩니다. 사용자는 관리 대상 계정(표준 계정)에서 설정 탭을 열고,
설정 탭은 그 세션의 agent를 거쳐 설정 파일을 고칩니다. **프로그램은 관리자 계정과 표준 계정을 구별하지 않습니다.**

**고치기, 임시 저장, 적용:** 설정 탭에서 고친 내용은 곧바로 설정이 되지 않습니다.
- 설정 탭은 설정을 설정 묶음으로 나눕니다. 묶음은 API 키, 모델, AI 하루 예산, 생활 규칙, 약속 규칙, 지시문 다섯 개(하나씩), 항상 막을 프로그램, 항상 막을 웹사이트, 지금 걸린 차단(차단 풀기), AI가 준 접근 허용(허용 취소), 접근 요청의 한도, 검사 간격과 판정, 검사하지 않는 앱, 비공개 앱, 브라우저입니다.
- 묶음마다 아래에 막대가 있습니다. 고친 내용이 있으면, 막대는 고친 내용을 한 줄에 하나씩 보여 주고(예: "strikes_to_block = 1", "blacklist: + steam.exe"), 각 줄 앞에 초록 "적용하면 바로" 또는 노란 "적용하면 예약"을 붙입니다. 그래서 사용자는 적용하기 전에 무엇이 바로 적용되고 무엇이 예약될지 압니다.
- 막대에는 임시 저장의 상태도 나옵니다. "임시 저장하는 중…", "자동으로 임시 저장됨 14:05:12 · 아직 적용 전입니다.", "저장됨 14:05:12 · 아직 적용 전입니다."(**저장** 버튼으로 저장했을 때), "임시 저장되어 있습니다 · 아직 적용 전입니다."(Focus 앱을 켤 때 되살린 내용) 중 하나입니다. API 키 묶음에는 "키는 임시 저장하지 않습니다."가 나옵니다.
- 막대의 버튼은 다음과 같습니다.
  - **저장**: 고친 내용을 지금 바로 임시 저장합니다. 자동 임시 저장과 같은 일을 하고, "14:05:12에 저장했습니다. "적용"을 눌러야 설정에 반영됩니다."라고 알려 줍니다.
  - **적용**: 그 묶음의 고친 내용만 agent에게 보냅니다(아래 "동작 방식" 4번). 다른 묶음에서 고친 내용은 보내지 않고 그대로 남깁니다.
  - **고친 것 버리기**: 그 묶음의 고친 내용을 버리고, 지금의 설정(예약된 업데이트를 더한 설정)으로 되돌립니다.
  - **기본값으로 되돌리기**: 프로그램에 기본값이 있는 묶음(모델, AI 하루 예산, 지시문, 접근 요청의 한도, 검사 간격과 판정, 검사하지 않는 앱, 비공개 앱, 브라우저)에서, 지금 값이 기본값과 다를 때만 보입니다. 이 버튼은 그 묶음을 기본값으로 고칩니다. 그것도 고친 내용이므로, 사용자가 **적용**을 눌러야 설정이 됩니다.
- **임시 저장 파일:** 설정 탭은 고친 내용을 1초 뒤 사용자 계정의 앱 데이터 폴더에 있는 `settings_drafts.json`(Windows에서는 `%LOCALAPPDATA%\DigitalWellbeing\DigitalWellbeing\data\settings_drafts.json`)에 씁니다. 이 파일에는 파일 전체가 아니라 설정 하나하나의 고친 내용만 들어갑니다. 설정 탭은 Focus 앱이 켜질 때 이 파일을 읽어서 고친 내용을 되살립니다. 그동안 설정 파일이 다른 곳에서 바뀌었으면(예: 다른 변경이 적용되거나 할 일이 추가됨), 설정 탭은 새 설정 위에 사용자의 고친 내용을 다시 얹습니다. **API 키는 이 파일에 쓰지 않습니다.**
- 예전 버전의 설정 탭에는 탭 아래쪽에 파일 전체를 저장하는 버튼 하나가 있었습니다. 지금은 그 버튼이 없고, 묶음마다 적용합니다.

적용한 변경이 언제 효력이 생기는지는 두 가지가 정합니다. 하나는 설정이 보호되어 있는지이고, 다른 하나는 그 변경이 규칙을 엄격하게 만드는지 느슨하게 만드는지입니다.

| 상태 | 설정 탭에서 적용하면 |
|---|---|
| **설정 단계** (`settings_protection.json`이 없음) | 모든 변경이 바로 적용됩니다. 화면 위에 "설정 단계: 변경이 바로 적용되고, 이 PC를 쓰는 누구나 설정을 바꿀 수 있습니다."라는 노란 안내가 보입니다. |
| **보호됨** | agent는 받은 파일을 설정 하나하나의 변경으로 나눕니다. **엄격한 변경은 바로 적용됩니다.** **느슨한 변경은 예약된 업데이트가 됩니다.** 사용자가 확인 질문에 이틀 간격으로 세 번 연속 "예"라고 답하면, 그때 그 변경이 적용됩니다. 화면 위에는 "설정이 보호되어 있습니다. 규칙을 더 엄격하게 만드는 변경은 바로 적용됩니다. 그 밖의 변경은 예약되고, …"라는 설명이 보입니다. |

**보호된 뒤에 느슨한 변경이 확인 질문을 거치는 이유:** 사용자가 순간적인 충동으로 차단을 풀거나 규칙을 느슨하게 바꿔도, 그 변경은 빨라도 6일 뒤에야 적용됩니다.
게다가 사용자는 그 변경을 서로 다른 세 날에 세 번 다시 승인해야 합니다. 그래서 충동적인 변경으로는 즉시 얻는 것이 없고, 사용자가 차분한 날에 그 변경을 거절할 기회가 세 번 있습니다.
반대로 사용자가 여러 날 동안 계속 원하는 변경(고친 생활 규칙 등)은 결국 적용됩니다.

**엄격한 변경을 바로 적용하는 이유:** 규칙을 더 엄격하게 만드는 변경으로는 충동적으로 얻는 것이 없습니다. 그런 변경까지 6일을 기다리게 하면, 사용자가 차분할 때 내린 좋은 결정(예: 게임을 블랙리스트에 넣기)이 늦어질 뿐입니다.

**어떤 변경이 엄격한가** (`machine::setting_edits`의 `direction()`): 아래 표에 없는 설정과, 어느 쪽인지 알 수 없는 변경은 모두 느슨한 변경으로 봅니다. 그래서 다음 변경은 언제나 예약됩니다.
API 키(`api_key`), 모델(`model`), 생활 규칙(`life_rules`), 약속 규칙(`appointment_rules`), 플래너 AI의 지시문(`instructions`), 브라우저 목록(`browsers`), 화이트리스트와 모드와 저장한 목록 묶음(`whitelist`, `mode`, `strategies`), 설정 파일을 거친 할 일 목록 변경(`todos`, `dismissed`).

| 파일 | 설정 | 바로 적용(엄격한 변경) | 예약(느슨한 변경) |
|---|---|---|---|
| `policy.json` | 블랙리스트(`blacklist`, "항상 막을 프로그램", 이름 또는 정규식) | 항목을 넣기 | 항목을 빼기 |
| `ai_focus.json` | 항상 막을 웹사이트(`always_blocked_sites`) | 항목을 넣기 | 항목을 빼기 |
| `ai_focus.json` | 앱을 끄기까지의 off_task 판정 수(`strikes_to_block`) | 줄이기 | 늘리기 |
| `ai_focus.json` | 시간 허용의 최대 길이(`max_grant_minutes`) | 줄이기 | 늘리기 |
| `ai_focus.json` | unsure 창을 다시 검사하기까지의 초(`check_interval_secs`) | 줄이기 | 늘리기 |
| `ai_focus.json` | on_task 창을 다시 검사하기까지의 분(`recheck_minutes`) | 줄이기. 0은 "unsure 창만큼 자주"라는 뜻이므로 가장 엄격합니다. | 늘리기 |
| `ai_focus.json` | 화면 캡처 보내기(`send_screenshot`) | 켜기 | 끄기 |
| `ai_focus.json` | 영구 허용을 줄 수 있음(`allow_permanent_grants`) | 끄기 | 켜기 |
| `ai_focus.json` | AI 검사의 하루 예산(`daily_budget_usd`) | 늘리기, 또는 0(예산 없음). 예산을 다 쓰면 AI 검사가 멈추므로, 예산이 클수록 검사가 오래 이어집니다. | 줄이기, 또는 0에서 금액으로 바꾸기 |
| `ai_focus.json` | 검사하지 않는 앱(`always_allow`)과 화면 캡처 없이 검사하는 앱(`private_apps`) | 앱을 빼기 | 앱을 넣기 |
| `ai_focus.json` | 취소한 접근 허용(`revoked_grants`, "허용 취소") | 넣기(허용 취소) | 빼기 |
| `ai_focus.json` | 푼 차단(`unblocked`, "차단 풀기") | 빼기("계속 막기") | 넣기(차단 풀기) |
| `planner.json` | 예전 플래너 켜기(`enabled`) | 켜기 | 끄기 |

`planner.json`의 `enabled`는 예전 버전에서 플래너를 켜고 끄던 값입니다. 지금은 플래너가 언제나 켜져 있으므로 agent는 이 값을 무시하고, 설정 탭에도 이 값을 고치는 칸이 없습니다([`task_planner.md`](task_planner.md) 4.1절). agent는 Claude Desktop이 보낸 파일 등에서 이 값이 바뀌어도 표대로 나누지만, 그 변경은 아무 효과가 없습니다.
| 모든 파일 | 고친 시각(`updated_at`) | 규칙과 관계없으므로 언제나 바로 적용됩니다. | — |

예를 들어 사용자가 "검사 간격과 판정" 묶음에서 "앱을 끄기까지의 off_task 판정 수를 2에서 1로 줄이기"와 "on_task 창을 다시 검사하기까지의 분을 15에서 30으로 늘리기"를 함께 적용하면, 판정 수는 바로 1이 되고 분의 변경만 예약됩니다.

- 설정 탭의 **지금 걸린 차단**에서 누르는 **차단 풀기**는 느슨한 변경이므로, 설정이 보호된 뒤에는 예약된 업데이트가 되어 빨라도 6일 뒤에 적용됩니다. 차단된 앱이나 사이트를 바로 써야 하면, 사용자는 목적을 적어 접근을 요청하고 AI의 승인을 받습니다([`access_grants.md`](access_grants.md)).
- **AI가 준 접근 허용**에서 누르는 **허용 취소**는 엄격한 변경이므로 바로 적용됩니다.
- 항상 막을 웹사이트에 항목을 넣는 것은 엄격한 변경이므로 바로 적용되고, 빼는 것은 느슨한 변경이므로 예약됩니다.
- 할 일 목록은 설정 파일(`planner.json`)에 있지만, 사용자는 할 일 탭에서 AI의 심사를 거쳐 고칩니다. AI가 승인한 할 일 변경은 이 표와 상관없이 바로 적용됩니다([`task_planner.md`](task_planner.md) 4.6절).

**설정을 보호하는 방법:** 사용자는 Focus 앱의 설정 탭 맨 위의 **설정 보호(잠금)** 영역에서 "프로그램 안의 어떤 것도 보호를 끄지 못한다는 것을 이해했습니다."를 체크한 뒤 **설정 보호하기**를 누릅니다.
- Focus 앱은 agent에게 `settings_protect`를 보내고, agent는 보호한 시각을 `settings_protection.json`에 씁니다.
- **프로그램 안에는 보호를 끄는 기능이 없습니다.** 보호는 한 방향입니다. 다시 `settings_protect`를 보내도 처음 보호한 시각이 그대로 남습니다.
- 설정 잠금이 있던 예전 버전에서 업데이트한 경우, 데이터 폴더에 예전 잠금 파일(`settings_lock.json`)이 있으면 agent는 설정이 보호된 것으로 봅니다. 잠금의 기한은 더 이상 쓰이지 않습니다.
  예전 버전이 "잠금이 끝날 때 적용"하려고 보관해 둔 변경(`settings_pending.json`)은, 저장했던 시각에 예약한 업데이트로 옮겨집니다. 이 업데이트도 같은 확인 질문을 거칩니다.

**예약된 업데이트와 확인 질문:**
- 예약된 업데이트는 파일 전체가 아니라 **설정 하나하나의 변경**을 담습니다. 업데이트가 적용될 때, agent는 그 변경을 **그때의 설정 파일**에 적용합니다. 그래서 업데이트를 기다리는 동안 바로 적용된 다른 변경(엄격한 변경, AI가 승인한 할 일 변경)은 지워지지 않고 남습니다.
- 설정이 보호된 뒤 사용자가 느슨한 변경을 적용하면, 그 묶음의 막대 아래에 "예약했습니다. 첫 질문은 2026-11-03 14:05에 옵니다."처럼 첫 질문이 오는 시각이 나옵니다. 엄격한 변경이 함께 있었으면 "1개는 바로 적용했고, 나머지는 예약했습니다. 첫 질문은 …에 옵니다."처럼 나옵니다. 모두 엄격한 변경이면 "적용했습니다. 지금부터 효력이 있습니다."가 나오고, agent가 거부하면 "적용하지 못했습니다: …"가 나옵니다.
- 설정 탭은 예약된 업데이트를 맨 위의 "예약된 업데이트" 아래에 하나씩 보여 줍니다. 각 업데이트에는 파일 이름(할 일 변경이면 "할 일 변경"), 예약한 시각과 예약한 곳(예: "설정 탭", "Claude Desktop", "할 일 탭"), 지금까지 받은 "예" 답의 수(예: "1/3번 확인"), 질문 간격("2일마다 질문" 또는 "2시간마다 질문")이 한 줄에 나오고, 그 아래에 다음 질문 시각("다음 질문: …")이 나옵니다. 할 일 변경이면 그 변경과 이유와 AI의 답을 적은 메모도 나옵니다.
- 각 업데이트의 **바뀌는 것**을 펼치면, 바뀌는 설정이 한 줄에 하나씩 보입니다. 예: "strikes_to_block = 3", "blacklist: − steam.exe", "always_allow: + zoom.exe", "todos: p1761830000000 = {…}". API 키는 "api_key = (새 키)"로만 보입니다. 질문할 때가 된 업데이트는 이 부분이 처음부터 펼쳐져 있습니다.
- 예약하고 이틀이 지나면(할 일 변경은 두 시간), 그 업데이트 아래에 빨간 글씨로 "planner.json의 이 업데이트가 정말 맞나요? (1/3번째 질문)"라는 확인 질문과 "위의 "바뀌는 것"을 읽고, 차분한 날의 나라면 어떻게 답할지 생각해서 답하세요."라는 안내가 나옵니다. 사용자는 **예, 여전히 원합니다** 또는 **아니요, 거절합니다**를 누릅니다.
  - 사용자가 "예"라고 답하면, 다음 질문은 그 답을 한 때부터 이틀 뒤(할 일 변경은 두 시간 뒤)에 옵니다. 세 번째 "예"를 받으면, agent는 그 변경을 그때의 설정 파일에 적용하고 형식을 한 번 더 검사한 뒤 씁니다. 모든 agent는 3초 안에 바뀐 파일을 다시 읽습니다.
  - 사용자가 한 번이라도 "아니요"라고 답하면, agent는 그 업데이트를 거절하고 버립니다. 지금의 설정은 그대로입니다.
  - 사용자가 질문에 답하지 않으면, 질문은 답할 때까지 기다립니다. 시간이 지나도 저절로 승인되거나 거절되지 않습니다.
  - 질문할 때가 되기 전에 답을 보내면, agent는 그 답을 거부합니다. 그래서 사용자는 질문 간격을 건너뛸 수 없습니다.
- 질문할 때가 되면, Focus 앱은 숨어 있던 창을 띄우고 설정 탭을 보여 줍니다. 할 일 탭에도 빨간 줄과 **설정 탭에서 답하기** 링크가 보입니다.
- 사용자는 언제든 **이 업데이트 거두기**를 눌러 예약된 업데이트를 거둘 수 있습니다. 거두기는 확인을 거치지 않습니다. 적용되지 않은 변경을 거둬도 얻는 것이 없기 때문입니다.
- 한 설정 파일에는 설정 탭의 적용과 Claude Desktop의 저장으로 생긴 예약된 업데이트(출처 `settings`)가 많아야 하나 있습니다. agent가 같은 파일을 다시 받으면 다음과 같이 됩니다.
  - 받은 파일의 느슨한 변경이 예약된 업데이트의 변경과 **같으면**, 그 업데이트와 지금까지 받은 "예" 답이 그대로 남습니다. 예를 들어 사용자가 같은 파일의 다른 묶음에서 엄격한 변경 하나만 적용하면, 그 변경은 바로 적용되고 예약된 업데이트는 그대로입니다. 설정 탭은 적용할 때 예약된 변경을 더한 파일 위에 그 묶음의 변경만 얹어 보내기 때문입니다.
  - 받은 파일에 느슨한 변경이 **하나도 없으면**, 예약된 업데이트는 거둔 것으로 처리됩니다.
  - 느슨한 변경이 **다르면**, 새 업데이트가 예전 업데이트를 대신합니다. 이때 예전 업데이트가 받은 "예" 답은 사라지고, 확인 질문은 처음부터 다시 시작합니다. 예를 들어 `planner.json`의 생활 규칙 변경이 예약되어 있는데 사용자가 지시문의 변경도 적용하면, 두 변경을 함께 담은 새 업데이트가 예전 업데이트를 대신하고 확인 질문은 처음부터 다시 옵니다.
- AI 없이 하기로 한 할 일 변경의 예약된 업데이트(출처 `todo_change`)는 설정을 적용해도 대신되지 않습니다. 이 업데이트는 그 할 일 변경 하나만 담고 있기 때문입니다.
- 설정 탭의 각 영역은 지금 적용된 설정에 그 파일의 예약된 업데이트(출처 `settings`)의 변경을 더한 내용을 보여 줍니다. 그래서 사용자는 예약해 둔 변경에 이어서 고칠 수 있습니다. 예약해 둔 변경을 그대로 두고 다른 것만 고치면, 위의 규칙대로 예약된 업데이트와 그 "예" 답이 남습니다.
- agent는 받은 파일과 지금의 파일을 모두 기본값을 채운 모양으로 바꾼 뒤 비교합니다(`settings::normalize`). 그래서 예전 버전이 쓴 파일에 없던 설정이 기본값으로 저장되어도, 그것을 변경으로 보지 않습니다.
- 예전 버전이 파일 전체로 보관한 예약된 업데이트는, agent가 읽을 때 설정 하나하나의 변경으로 바뀝니다.
- agent는 업데이트가 어떻게 끝났는지(적용됨, 거절됨, 거둠, 새 업데이트로 대체됨)를 최근 50개까지 기록합니다.
- 작업 계정 사용자는 Windows 시계를 바꿀 수 없습니다(그 권한은 관리자 계정에만 있습니다). 그래서 사용자는 시계를 앞으로 돌려 질문을 앞당길 수도 없습니다.
- 환경 변수 `DW_SETTINGS_CONFIRM_INTERVAL_SECONDS`가 있으면, agent는 이틀이나 두 시간 대신 그 초만큼 기다립니다. 이 변수는 자동 테스트만을 위한 것입니다. 머신 설치에서 agent의 환경 변수는 SYSTEM 서비스의 환경 변수이고, 이것은 관리자만 바꿀 수 있습니다.

**솔직한 한계:** Windows는 관리자 계정이 서비스를 멈추거나 `C:\ProgramData\DigitalWellbeing\settings_protection.json`이나 설정 파일을 지우고 고치는 것을 막지 못합니다.
그래서 사용자는 표준 계정에서 일하고, 관리자 계정은 설치할 때와 관리 대상 계정을 바꿀 때(`install --manage` 또는 `machine.json`)만 씁니다.
관리 대상 계정 목록(`machine.json`)은 설정 탭에서 고칠 수 없습니다. 또 ProgramData 폴더의 로그를 읽을 때도 관리자 계정이 필요합니다.

**동작 방식** (`machine::settings`, `machine::setting_edits`, `apps/focus/src/settings.rs`):
1. Focus 앱은 관리자 권한이 없으므로 ProgramData 폴더를 열 수 없습니다. 대신 설정 탭이나 통계 탭이 보이는 동안, Focus 앱은 3초마다 agent에게 `settings_get`을 보냅니다. agent는 SYSTEM 권한으로 설정 파일 세 개(`policy.json`, `ai_focus.json`, `planner.json`), 설정이 보호되어 있는지, 예약된 업데이트와 지난 결과 기록, 화면에 필요한 읽기 전용 파일(`planner_state.json`, 사용자별 허용·차단·사용량 파일)을 읽어서 돌려줍니다. 설정이 보호되어 있어도 돌려줍니다.
2. 설정 탭은 받은 설정 파일 세 개로 화면에서 고칠 사본을 메모리에 만듭니다. 이때 각 파일에 그 파일의 예약된 업데이트(출처 `settings`)의 변경을 더하고, 임시 저장 파일에 남은 고친 내용을 그 위에 얹습니다. 설정 탭은 사용자 계정의 폴더에 설정 파일을 쓰지 않고, 고친 내용만 임시 저장 파일에 씁니다.
3. 사용자가 화면에서 설정을 고치면, 설정 탭은 처음 받은 사본과 지금의 사본을 비교해서(`setting_edits::diff`) 고친 내용을 묶음마다 그 막대에 보여 줍니다. 설정이 보호되어 있으면, 설정 탭은 agent와 같은 함수(`setting_edits::direction`)로 각 변경이 "적용하면 바로"인지 "적용하면 예약"인지 정해서 보여 줍니다. 고친 뒤 1초가 지나면 설정 탭은 고친 내용(API 키는 빼고)을 임시 저장 파일에 씁니다.
4. 사용자가 묶음의 **적용**을 누르면, 설정 탭은 먼저 `settings_get`으로 그 파일의 지금 내용을 다시 받습니다. 그사이 다른 곳에서 파일이 바뀌었을 수 있기 때문입니다. 설정 탭은 그 내용에 예약된 업데이트의 변경을 더하고, 그 위에 **그 묶음의 고친 내용만** 얹은 파일 전체를 `settings_put`(`via: "settings tab"`)으로 agent에게 보냅니다. 다른 묶음의 고친 내용은 보내지 않고, 화면과 임시 저장 파일에 그대로 남습니다.
   **고친 것 버리기**를 누르면, 설정 탭은 그 묶음만 처음 받은 사본의 값으로 되돌립니다.
5. agent는 내용이 그 설정의 형식에 맞는지 확인합니다. 형식에 맞지 않으면 설정 단계이든 보호된 뒤이든 거부합니다. 그다음 agent는 지금의 파일과 보낸 파일을 기본값을 채운 모양으로 바꾸고, 둘을 비교해서 설정 하나하나의 변경으로 나눕니다(`setting_edits::diff`).
   - 설정 단계이면, agent는 진짜 설정 파일을 씁니다.
   - 보호되어 있으면, agent는 엄격한 변경을 지금의 파일에 바로 적용합니다(`apply_now`). 느슨한 변경은 위의 규칙대로 예약된 업데이트로 저장하거나, 예약된 업데이트를 그대로 두거나, 거두거나, 대신합니다. 느슨한 변경은 진짜 설정 파일에 쓰지 않습니다.
   - agent는 `{ "applied": [바로 적용된 변경], "scheduled": { "id": 업데이트 번호, "first_question_at": 첫 질문 시각, "edits": [예약된 변경] } }`로 답합니다. 예약된 변경이 없으면 `scheduled`는 `null`입니다. 다른 agent들도 3초 안에 바뀐 파일을 다시 읽습니다.
6. Focus 앱은 `settings_get`으로 예약된 업데이트를 새로 받아 오고, 질문할 때가 된 업데이트에 확인 질문을 보여 줍니다. agent의 상태(`status`)에도 설정이 보호되어 있는지(`settings_protected`)와 질문할 때가 된 업데이트의 수(`settings_questions_due`)가 들어 있습니다. Focus 앱은 이 수가 늘면 창을 띄웁니다.
7. 사용자가 확인 질문에 답하면, Focus 앱은 `settings_answer`(업데이트 번호와 "예"/"아니요")를 보냅니다. agent는 질문할 때가 되었는지 확인하고, 아직 이르면 거부합니다.
   - "예"이면 agent는 답한 시각을 기록합니다. 세 번째 "예"이면, agent는 업데이트의 변경을 그때의 설정 파일에 적용하고, 한 번 더 형식 검사한 뒤 진짜 설정 파일에 쓰고, 업데이트를 "적용됨"으로 기록합니다.
   - "아니요"이면 agent는 업데이트를 지우고 "거절됨"으로 기록합니다.
8. **이 업데이트 거두기**를 누르면, Focus 앱은 `settings_withdraw`를 보내고, agent는 그 업데이트를 지우고 "거둠"으로 기록합니다. 업데이트에 답하거나 업데이트를 거두면, Focus 앱은 지금 맞는 내용으로 화면을 다시 만듭니다.
9. 할 일 변경은 이 길을 거치지 않습니다. 할 일 탭은 `todo_change`를 보내고, AI가 승인하면 agent가 그 변경을 바로 적용합니다(`apply_now`). 사용자가 AI 없이 하기로 하면(`todo_change_schedule`), agent는 그 변경을 두 시간 간격의 예약된 업데이트로 만듭니다(`schedule`). 자세한 내용은 [`task_planner.md`](task_planner.md) 4.6절에 있습니다.

**테스트** (`crates/machine/src/settings.rs`, `crates/machine/src/setting_edits.rs`):

| 테스트 이름 | 이 테스트가 확인하는 것 |
|---|---|
| `diff_then_apply_reproduces_the_new_file` | 두 파일의 차이를 설정 하나하나의 변경으로 나눈 뒤 예전 파일에 적용하면 새 파일과 같아진다(값, 이름 목록, `id`로 구별하는 할 일 목록). 같은 파일끼리는 변경이 없다. |

| `once_protected_stricter_edits_apply_at_once_and_looser_ones_are_scheduled` | 보호된 뒤 한 번에 저장한 변경 중 엄격한 변경(앱을 끄기까지의 판정 수 줄이기, 검사하지 않는 앱 빼기)은 바로 적용되고, 느슨한 변경(모델 바꾸기)만 예약된다. 같은 느슨한 변경과 엄격한 변경 하나를 더 저장하면, 예약된 업데이트와 "예" 답이 그대로 남는다. |
| `missing_defaults_in_the_file_in_force_are_not_changes` | 예전 버전이 쓴, 설정이 빠진 파일 위에 설정 탭이 기본값을 채운 파일을 보내도, 실제로 바꾼 설정 하나만 변경으로 본다. |
| `a_protected_edit_takes_effect_after_three_yes_answers_two_days_apart` | 보호된 뒤 생활 규칙의 변경은 예약된다. 질문할 때가 되기 전의 답은 거부되고, 질문은 답할 때까지 기다리고, 다음 질문은 답한 때부터 이틀 뒤이며, 세 번째 "예"에서 적용된다. |
| `one_no_rejects_and_other_looser_edits_start_over` | 보호는 다시 눌러도 처음 시각이 남는다. 다른 느슨한 변경을 저장하면 예약된 업데이트가 대신되고 "예" 답이 사라진다. "아니요" 한 번이면 거절된다. 느슨한 변경 없이 다시 저장하면 예약된 업데이트를 거둔다. |

**주의:** 보호 파일이 없으면 설정 단계입니다. 그래서 이 프로그램을 처음 설치하면, 사용자가 설정을 보호하기 전까지 이 PC의 누구든 작업 계정에서 고친 설정이 바로 적용됩니다.
사용자는 설치한 뒤 Focus 앱의 설정 탭에서 설정을 마치고(4.3절) 설정을 보호하세요.

### 6.5 프로그램 업데이트와 시간대 지키기 (`machine::system_care`)

이 절에서 **winget**은 Windows에 들어 있는 프로그램 관리 도구(앱 설치 관리자, App Installer)를 말합니다. **winget 이름(id)**은 winget이 프로그램마다 붙이는 이름입니다. 예를 들어 카카오톡의 이름은 `Kakao.KakaoTalk`입니다. 사용자는 명령 프롬프트에서 `winget search 카카오톡`을 실행해 "ID" 칸에서 이름을 찾습니다.

**프로그램 업데이트.** 작업 계정은 표준 계정이므로, 카카오톡처럼 업데이트에 관리자 권한이 필요한 프로그램을 스스로 업데이트하지 못합니다. 이 앱은 사용자에게 관리자 권한을 주지 않습니다. 관리자 권한을 잠깐이라도 주면, 그동안 사용자가 이 앱을 지우거나 시계를 바꾸거나 관리자 계정을 하나 더 만들 수 있기 때문입니다. 대신 서비스가 정해진 프로그램만 업데이트합니다.
1. 사용자는 Focus 앱의 설정 탭 → **시스템** → **프로그램 업데이트**에 winget 이름을 넣고 적용합니다. 설정이 보호되어 있으면 넣기는 느슨한 변경이므로 예약되고, 빼기는 바로 적용됩니다.
2. 사용자가 그 아래의 **지금 업데이트**를 누르면, agent가 데이터 폴더의 `update_requests\<번호>.json`에 요청을 씁니다. agent는 목록에 없는 프로그램의 요청을 거부합니다.
3. 서비스는 5초마다 요청을 찾고, `winget upgrade --id <이름> --exact --source winget --silent …`를 SYSTEM 권한으로 실행합니다. 서비스는 세션 0(사용자가 볼 수 없는 화면)에서 돌므로, 설치 프로그램이 창을 띄워도 사용자가 그 창을 쓸 수 없습니다. 그래서 설치 창의 파일 대화상자 같은 것으로 관리자 권한을 얻을 길이 없습니다. winget은 내려받은 설치 파일이 winget 목록에 적힌 해시와 같은지 확인합니다.
4. 서비스는 결과(업데이트함, 이미 최신, 설치되어 있지 않음, 실패와 winget의 마지막 출력)를 `system_care.json`에 남기고, 설정 탭은 최근 결과를 보여 줍니다. 30분 안에 끝나지 않는 업데이트는 멈춥니다.
5. **하루 한 번 저절로 업데이트하기**가 켜져 있으면(기본값), 서비스는 하루에 한 번, 새벽 4시 이후 PC가 켜져 있는 첫 때에 목록의 프로그램을 모두 업데이트합니다. 업데이트하는 동안 그 프로그램이 닫힐 수 있습니다.
- 서비스는 업데이트(`upgrade`)만 합니다. 지우기, 새로 설치하기, 다른 명령은 하지 않습니다. 이름은 글자, 숫자, `.`, `-`, `_`, `+`만 받습니다.
- winget이 없거나(앱 설치 관리자가 없는 PC), SYSTEM 계정에서 winget이 동작하지 않으면 업데이트는 "실패"로 남습니다.

**시간대 지키기.** 표준 사용자는 시계는 바꾸지 못하지만 Windows의 시간대는 바꿀 수 있습니다. 시간대를 바꾸면 생활 규칙의 시각(예: "평일 18시 전에는 게임을 할당하지 않는다")을 피할 수 있습니다.
1. 설정의 `time_zone`(설정 탭 → **시스템** → **시간대 지키기**)이 비어 있으면, 서비스는 처음 돌 때 PC의 시간대를 그 칸에 적습니다.
2. 그 뒤로 서비스는 5초마다 PC의 시간대를 읽고, 설정과 다르면 `tzutil /s`로 되돌립니다. 일광 절약 시간 끄기(이름 끝의 `_dstoff`)도 시간대의 일부로 봅니다. 되돌린 기록은 설정 탭에 나옵니다.
3. 여행 등으로 시간대를 바꿔야 하면, 사용자는 설정 탭에서 지킬 시간대를 고칩니다. 설정이 보호되어 있으면 이 변경은 예약되고, 세 번 확인한 뒤에 적용됩니다.

## 7. 한계와 주의점

1. **개발자는 실제 Windows에서 아직 확인하지 않았습니다**(맨 위 경고). 특히 SYSTEM 권한의 agent가 사용자 화면을 캡처하고(`xcap`)
   키 입력을 보낼 수 있는지(`SendInput`) 확인해야 합니다.
2. **AI는 할 일 목록과 생활 규칙에 비추어 판단합니다.** 사용자가 "유튜브 보기" 같은 할 일을 추가하려 하면, AI가 생활 규칙에 비추어 심사합니다. 생활 규칙이 막연하면 AI가 그런 할 일을 승인할 수 있고, 그 할 일이 할당되면 AI 검사도 유튜브를 허용합니다.
   어떤 경우에도 반드시 막아야 하는 프로그램과 웹사이트는, 사용자가 설정 탭에서 **항상 막을 프로그램**과 **항상 막을 웹사이트**에 넣고 설정을 보호해야 합니다.
3. **이 프로그램은 컴퓨터를 직접 만지는 우회를 스스로 막지 못합니다.** 예를 들어 사용자가 안전 모드로 부팅하면 서비스가 시작되지 않고, USB로 다른 운영체제를 띄우면 이 프로그램은 실행되지 않습니다.
   관리자는 4.4절의 방법(BIOS 비밀번호와 USB 부팅 끄기, 안전 모드로 들어가는 길 막기, BitLocker)으로 이런 우회를 막습니다.
4. **agent는 차단할 때 같은 이름의 프로그램을 그 세션 안에서 모두 끕니다.** 한 사람이 세션 하나를 쓴다면 문제가 없습니다.
5. **화면이 잠겨 있거나 다른 계정으로 전환된 동안에는**, agent가 지금 보는 창을 찾지 못하거나 화면이 검게 캡처될 수 있습니다.
   그러면 AI의 판정이 이상할 수 있습니다(대개 "모르겠음"). 하지만 그 시간에는 사용자가 작업 계정을 쓰고 있지 않습니다.
6. **agent의 로컬 포트는 같은 컴퓨터의 다른 계정도 접속할 수 있습니다.** agent는 `127.0.0.1:(8770 + 세션 번호)`에서 요청을 받습니다.
   다른 계정이 이 포트에 접속해도, 그 계정이 할 수 있는 일은 그 세션의 데일리 웰빙, 할 일 플래너, 접근 요청, 설정 요청뿐입니다. 설정이 보호되어 있으면, 그 계정이 저장한 느슨한 변경도 예약된 업데이트가 됩니다.
   할 일 변경도 같습니다. 다른 계정이 보낸 할 일 변경도 AI가 심사하고, AI가 승인하지 않은 변경을 AI 없이 하기로 하는 요청(`todo_change_schedule`)도 세 번의 확인 질문을 거칩니다.
   다만 확인 질문에 답하는 요청(`settings_answer`)도 같은 포트로 받으므로, 다른 계정도 질문할 때가 된 업데이트에 답할 수 있습니다. 그래도 이틀 간격은 건너뛸 수 없습니다.
   설정 단계에서는 이 PC의 어느 계정이든 `settings_put`으로 설정을 바로 바꿀 수 있습니다. 설정 탭이 "이 PC를 쓰는 누구나 설정을 바꿀 수 있습니다"라고 안내하는 이유입니다.
   남은 할 일이 있으면, 다른 계정도 이유를 적고 AI의 승인을 받아야 지금 할 일을 바꿀 수 있습니다.
7. **단독 실행 모드의 8765 API에는 인증이 없습니다.** 머신 설치는 `digital-wellbeing.exe`를 설치하지 않고, 서비스가 등록된 PC에서 이 파일을 실행해도 안내 창만 뜨므로, 이 API가 열리지 않습니다.
   하지만 누군가 소스에서 빌드한 `digital-wellbeing.exe`를 `--standalone` 옵션으로 강제로 실행하면 이 API가 다시 열립니다. 공유 컴퓨터에서는 이 옵션을 쓰지 마세요.
8. **프로그램은 로그 파일을 나누어 보관하지 않습니다.** 로그 파일이 10MB를 넘으면, 프로그램은 다음에 시작할 때 그 파일을 비웁니다.
9. **코드 검토에서 나왔지만 아직 고치지 않은 점:**
   - **agent가 서비스에 묶여 있지 않습니다.** 서비스 프로세스가 비정상 종료되면, Windows가 서비스를 다시 시작하면서 각 세션에 agent를 하나 더 띄울 수 있습니다. 이때 남은 agent가 포트를 잡고 있어서, 새 agent의 Focus 앱 통신이 열리지 않습니다.
   - **agent가 SYSTEM의 특수 권한을 모두 가지고 돕니다.** agent에게는 그 권한이 필요하지 않으므로, 권한을 줄이는 편이 안전합니다.
   - **서비스는 계속 꺼지는 agent를 2초마다 다시 띄웁니다.** 다시 띄우는 간격을 점점 늘리는 장치가 없어서, 그런 경우 로그가 빠르게 커집니다.
